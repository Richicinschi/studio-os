# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting: open the repository's Security tab, then "Report a vulnerability". Please do not open a public issue for a vulnerability, and do not put one in a pull request.

A useful report holds:

- the file and line;
- what an attacker can do with it;
- how to reproduce it.

A fix ships in the next release; `CHANGELOG.md` records it. No response time is promised.

## Scope

In scope:

- the kit's own skills (`.claude/skills/`);
- the templates (`templates/`), above all `templates/git-hooks/` and `templates/hooks/`;
- the export tooling (`tools/`);
- the shipped copies in `catalog/`;
- advice in the cards or modules that would lead an adopter into an unsafe setup.

Out of scope:

- the upstream projects behind the third-party skills: report to them (`docs/THIRD_PARTY_NOTICES.md` lists them);
- Claude Code itself;
- an adopter's own setup.

## Checking that your copy is the release

The kit runs in your Claude Code session before anything in it is scanned, so it is worth checking that your copy is the one published. Every commit on the public repository's `main` is signed with one OpenPGP key:

- **The key:** primary key fingerprint `991E 1809 86B7 7CE9 9299 3AEB 2E92 6BA8 8C6D 6423`, key id `2E926BA88C6D6423`. gpg prints the fingerprint with two spaces in the middle, and without spaces on its "using RSA key" line: `991E180986B77CE992993AEB2E926BA88C6D6423`.
- **Where it is published:** at `https://github.com/Richicinschi.gpg`, the public keys of the maintainer's GitHub account, and as the "Verified" mark GitHub shows on each commit of the repository. That address also holds two other keys of the same account, which sign no release. Importing it imports all three, and a good signature from any of them makes `git verify-commit` succeed, so a pass is a good signature with the fingerprint above, not the exit code alone.
- **Expiry:** 2027-05-20. A new key will be announced in a release signed by this one. After that date gpg still prints `Good signature`, with `[expired]` after the name and `Note: This key has expired!`, and `git verify-commit` still exits 0. That means the commit was signed while the key was valid: check that the `Signature made` date is before 2027-05-20 and that the fingerprint is the one above.
- **What else gpg may print:** `BAD signature` means the commit was changed after it was signed, so it is not the release. `WARNING: This key has been revoked by its owner!` under a good signature means the key was withdrawn: treat the copy as not the release, and look for the announcement of the new key.
- **Tags:** v3.0.0 to v3.1.1 are signed tags, and so is every tag from v3.4.0 on: check one with `git verify-tag <tag>`. v2.0.3, and v3.2.0 to v3.3.0 (made by `gh release create`), are plain tags on signed commits: check the commit with `git verify-commit <tag>`.

How to import the key and check your clone, in Git Bash, macOS and Linux, and Windows PowerShell: [START-HERE.md](START-HERE.md#your-first-session), "Your first session", step 1. An update run (`drill-to-adopt`, "Update my adoption") runs the same check on the kit and reports the result without stopping. A pass covers the commit and every file in it. It means something only in a clone you made yourself with `git clone` from the public repository's address (START-HERE.md, step 1): a copy you received any other way is cloned again, not checked, because its `.git` folder chooses the program that checks it (`gpg.program`) and can run a command of its own when you run `git status` (`core.fsmonitor`). `git status --ignored` in your clone shows files that differ from the commit, ignored ones included.

## What is enforced and what is asked

The kit offers two kinds of protection, and they are not the same.

- **Enforced by code:** a script or a setting refuses or reports, whatever Claude intends. It still has gaps, listed below.
- **Asked:** an instruction Claude follows. An instruction is not a lock: Claude Code can read and edit every file in a folder you add, as `START-HERE.md` says of the audit. Treat an asked rule as a habit that Claude keeps, and check it when it matters.

## Reading this list

- A hook is a floor, not a wall. Git hooks do nothing when skipped; a Claude Code hook runs only in Claude Code, so a terminal you open yourself is outside it.
- Run `canary.mjs` and the guard's own test (`git-guardrails` SKILL.md, step 5) after any change, as a guard that silently stopped matching looks like one that works.

## Threats, and what covers each

The tables above are ordered by mechanism; this one is ordered by threat.

- **What the kit protects:** your secrets (keys, tokens, `.env` files), the private names in your work (clients, employers, people), your repositories and their history, and your Claude setup (instructions, settings, hooks, skills).
- **From what:** an outside skill, plugin, MCP server or hook that does more than it says; instructions hidden in what Claude reads; and Claude's own mistakes.
- **Where the boundaries are:** whatever a session reads can reach the model and the session transcript, and whatever runs in a session (a skill's script, a hook, an MCP server) runs with your rights. The kit's enforced mechanisms sit at three points: Claude Code's settings and hooks, git's hooks, and GitHub's settings. A terminal you open yourself is outside the first; a skipped hook or a clone without the hooks is outside the second.
