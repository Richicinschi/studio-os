# Facts the kit depends on

These change. Every fact here has its source and the date it was last checked, after "checked", "read", "as of", "tried" or "observed ... on". ## Models: which for what

- The current models are Claude Fable 5.2 (`claude-fable-5-2`), Opus 5.5 (`claude-opus-5-5`), Sonnet 5.5 (`claude-sonnet-5-5`) and Haiku 5.5 (`claude-haiku-5-5`). Fable 5.1 is in the page's "All models" table below them, under "Older models might still be available, but where possible, you should default to the latest models." (checked 2026-11-25, [source](https://platform.claude.com/docs/en/models/overview))
- Anthropic's starting advice: "If you’re unsure which model to use, start with Claude Opus 5.5 for most workloads. Use Claude Fable 5.2 for demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5.5 at higher effort still fall short." (checked 2026-11-25, [source](https://platform.claude.com/docs/en/models/overview))
- By kind of task: Fable 5.2 for agent sessions that run for hours and multistep deep research; Opus 5.5 for multihour autonomous coding, large refactors and computer use; Sonnet 5.5 for code generation, data analysis and content; Haiku 5.5 for real-time, high-volume, cost-sensitive work and subagent tasks. (checked 2026-11-25, [source](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model))
- In Claude Code the model aliases are `opus` (complex reasoning), `sonnet` (daily coding), `haiku` (simple tasks) and `fable` (the hardest and longest-running tasks). (checked 2026-11-02, [source](https://code.claude.com/docs/en/model-config))
- Claude Code's default model on the Pro, Max, Ultra, Team and Enterprise plans and on the API is Opus 5.5; Fable is the default on none. (checked 2026-11-02, [source](https://code.claude.com/docs/en/model-config))
- Claude Code's effort levels: `medium` fits day-to-day work with a clear scope, `high` fixing a bug in an existing codebase, and `max` finding security vulnerabilities, though it is "prone to overthinking". (checked 2026-11-02, [source](https://code.claude.com/docs/en/model-config))
- The claude.ai model menu: you pick a model by its name next to the send button, and "More models" shows the rest. The page no longer lists the menu's models; its effort selector "is available for Claude Fable 5.2, Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable 5.1, Opus 5, Sonnet 5, Fable 5, Opus 4.7, Opus 4.6, and Sonnet 4.6." Which plan gets which model, and the claude.ai default: not documented as of 2026-11-25. ([source](https://support.claude.com/en/articles/8664678-how-can-i-change-the-model-version-that-i-m-chatting-with))
- The context window of each current model (Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5) is 1M tokens. In Claude Code, "Fable models, Sonnet 5 and later, Haiku 5.5, and Opus 4.7 and later run with the 1M window by default"; `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` keeps sessions at a 200K window. (checked 2026-11-25, [source](https://platform.claude.com/docs/en/models/overview), [source](https://code.claude.com/docs/en/model-config))

## Prompt cache and why a new day starts cold

- In Claude Code the main conversation's cache lives one hour on a Claude subscription within plan usage, and five minutes on usage credits, an API key or a cloud provider; subagents' caches live five minutes. (checked 2026-11-02, [source](https://code.claude.com/docs/en/prompt-caching))
- Each cache hit resets the timer; "after a long enough gap, the next request recomputes the full input and re-establishes the cache." (checked 2026-11-02, [source](https://code.claude.com/docs/en/prompt-caching))
- So a conversation resumed the next day is past every cache lifetime, and its first request reprocesses the whole history with no cache hits. How that counts against a subscription's usage: not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/prompt-caching))
- Compacting after a long break "reprocesses that history as uncached input. This is why /compact costs the most when you resume an old session." (checked 2026-11-02, [source](https://code.claude.com/docs/en/prompt-caching))
- Switching model with `/model` makes the next request read the entire conversation with no cache hits. (checked 2026-11-02, [source](https://code.claude.com/docs/en/prompt-caching))
- To see which cache lifetime applies to you: `claude -p "hello" --output-format json`, then read `usage.cache_creation`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/prompt-caching))
- On the API, a cache write costs 1.25 times the input price for five minutes and 2 times for one hour; a cache read costs 0.1 times (0.05 on Opus 5.5 and Sonnet 5.5, 0.025 on Fable 5.2 and Fable 5.1); the default lifetime is five minutes. (checked 2026-11-25, [source](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))
- claude.ai: "Content in projects is cached and counts less against your limits when reused." "Caches expire after a period of inactivity. If you come back to a project after a long break, your first message counts that content in full again." (read 2026-11-25, [source](https://support.claude.com/en/articles/9797557-usage-limit-best-practices))
- How long claude.ai's cache lives, and whether a chat's own earlier messages are cached: not documented as of 2026-11-25; searched [Usage limit best practices](https://support.claude.com/en/articles/9797557-usage-limit-best-practices), [What are projects?](https://support.claude.com/en/articles/9517075-what-are-projects). The first page lists "Claude remembers context from earlier in the conversation" under its caching line, without more.

## Claude Code: context commands, subagents, extra folders

- `/clear` starts a new conversation with empty context and keeps project memory; its aliases are `/reset` and `/new`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/commands))
- `/compact [instructions]` frees context by summarizing the conversation so far, optionally focused by the instructions you pass. (checked 2026-11-02, [source](https://code.claude.com/docs/en/commands))
- Claude Code compacts automatically as the conversation nears its context limit; `/autocompact` sets an earlier trigger, for example `/autocompact 500k`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/model-config))
- After a compaction the project-root `CLAUDE.md`, unscoped rules and auto memory are read again from disk, up to five recent files are re-read, and skill bodies are capped at 5,000 tokens each and 25,000 in all. Instructions given only in the conversation can be lost. (checked 2026-11-02, [source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/memory))
- A subagent works in its own context window; only its summary and a small metadata trailer come back to the main conversation. (checked 2026-11-02, [source](https://code.claude.com/docs/en/context-window))
- `--add-dir` gives Claude read and edit access to more folders, for example `claude --add-dir ../apps ../lib`; the reference adds that Claude Code does not discover most `.claude/` configuration from them. (checked 2026-11-02, [source](https://code.claude.com/docs/en/cli-reference))
- The pages differ on what an added folder brings: the skills page says skills in its `.claude/skills/` load, and the memory page says its `CLAUDE.md` loads only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/skills), [source](https://code.claude.com/docs/en/memory))
- Picking up and undoing, from the commands page: `/resume [session]` will "Resume a conversation by ID or name, or open the session picker"; `/rewind` will "Rewind the conversation and/or code to a previous point, or summarize from a selected message" (aliases `/checkpoint`, `/undo`); `/plan [description]` will "Enter plan mode directly from the prompt". (read 2026-11-25, [source](https://code.claude.com/docs/en/commands))

## Claude Code: where skills, agents and instruction files load from

- Project skills are `.claude/skills/<name>/SKILL.md`, found in the folder Claude Code starts in and in every parent folder up to the repository root; skills in nested subfolders load when Claude works in that subfolder. (checked 2026-11-02, [source](https://code.claude.com/docs/en/skills))
- User skills are `~/.claude/skills/<name>/SKILL.md`, for every project on the machine. When two have the same name, enterprise wins over personal, and personal over project. (checked 2026-11-02, [source](https://code.claude.com/docs/en/skills))
- Subagents are Markdown files with YAML front matter (`name` and `description` required; the body is the subagent's instructions): `.claude/agents/<name>.md` for a project, `~/.claude/agents/<name>.md` for every project. (checked 2026-11-02, [source](https://code.claude.com/docs/en/sub-agents))
- A subagent's `tools` field is an allowlist of the tools it may use, written as `Read, Grep, Bash` or as a YAML list. Left out, the subagent "inherits every tool available to subagents". `disallowedTools` is a denylist, applied first. Some tools never reach a subagent even when listed, `AskUserQuestion` among them. `Bash` "executes shell commands in your environment", so a subagent given `Bash` can change files without `Write` or `Edit`; a `Bash(git push *)` entry in `disallowedTools` "still removes the whole tool". (checked 2026-11-02, [source](https://code.claude.com/docs/en/sub-agents), [source](https://code.claude.com/docs/en/tools-reference))
- A subagent's `model` field takes `sonnet`, `opus`, `haiku`, `fable`, a full model ID, or `inherit` ("use the same model as the main conversation"). Left out, the model is, in order: the one Claude passes for that call, if any; `CLAUDE_CODE_SUBAGENT_MODEL`, if you set it; otherwise the main conversation's model. (checked 2026-11-02, [source](https://code.claude.com/docs/en/sub-agents))
- Claude Code ignores a subagent front matter field it does not recognize, without an error. (checked 2026-11-02, [source](https://code.claude.com/docs/en/sub-agents))
- "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation." Claude resumes a subagent with the `SendMessage` tool, and "a subagent that has the `SendMessage` tool can send that message too". (checked 2026-11-02, [source](https://code.claude.com/docs/en/sub-agents))
- The nesting depth is a setting: "To change the limit, set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to the number of subagent layers you want below your main conversation"; "Set 1 to turn nesting off." At the limit, "Claude Code withholds the Agent tool from every subagent except a fork". (read 2026-11-25, [source](https://code.claude.com/docs/en/sub-agents))
- Claude Code's built-in subagents include `general-purpose`, "A capable agent for complex, multi-step tasks that require both exploration and action", with "every tool available to subagents", and the read-only `Explore` and `Plan`. The hooks reference names them too: "For built-in agents, this is the agent name like `general-purpose`, `Explore`, or `Plan`." "Built-in subagents are registered by default in interactive sessions"; a `permissions.deny` entry blocks one type, and in non-interactive mode and the Agent SDK, `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` removes them all. (read 2026-11-25, [source](https://code.claude.com/docs/en/sub-agents), [source](https://code.claude.com/docs/en/hooks))
- Which a subagent follows when its own instructions and the task message Claude writes for it ask for different things, such as two output formats: not documented as of 2026-11-25; searched [Create custom subagents](https://code.claude.com/docs/en/sub-agents). That page says a non-fork subagent starts with a "System prompt: the agent's own prompt plus environment details that Claude Code appends" and a "Task message: the delegation prompt Claude writes when it hands off the work".
- Whether the claude.ai chat app (as opposed to Claude Code) has subagents: not documented as of 2026-11-02; the subagent pages describe Claude Code only. ([source](https://code.claude.com/docs/en/sub-agents), [source](https://code.claude.com/docs/en/feature-availability))
- `disable-model-invocation: true` in a skill's front matter: "Claude can't invoke the skill on its own"; you still run it by typing `/<name>`. Its description is then not in context, and the full skill loads when you invoke it. (checked 2026-11-02, [source](https://code.claude.com/docs/en/skills))
- `CLAUDE.md` and `CLAUDE.local.md` load at launch from the working folder and every folder above it, root first; those in subfolders load when Claude works there. (checked 2026-11-02, [source](https://code.claude.com/docs/en/memory))
- `AGENTS.md` is read only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working folder or above (Claude Code v2.1.277 and later); the setting value `claude-md-and-agents-md` loads both. The documented way to keep one shared file is a `CLAUDE.md` that contains the line `@AGENTS.md`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/memory))

## Claude Code: installed plugins and their skills

Checked 2026-11-20.

- Claude Code keeps plugin files under a plugins root, `~/.claude/plugins`, "unless you set `CLAUDE_CODE_PLUGIN_CACHE_DIR`". Despite its name, that variable "sets the parent directory, not the cache itself". `CLAUDE_CONFIG_DIR` moves `~/.claude`, plugins included. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins/loading), [source](https://code.claude.com/docs/en/env-vars))
- An installed marketplace plugin is copied to `cache/<marketplace>/<plugin>/<version>/` under that root, one folder per installed version; `${CLAUDE_PLUGIN_ROOT}` points there. `installed_plugins.json`, in the root, records each install with its `scope`, `installPath` and `version`. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins/loading))
- A plugin's skills sit in its `skills/` folder, "One `<name>/SKILL.md` per skill". So an installed plugin's skill is at `<plugins root>/cache/<marketplace>/<plugin>/<version>/skills/<name>/SKILL.md`, and its agents at `.../agents/<name>.md`. A plugin's manifest can add other skill folders (`skills` key), and a plugin with a `SKILL.md` at its root and no `skills/` loads as one skill. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins-reference))
- Plugins synced from a claude.ai account are under `~/.claude/plugins/synced/`, which stays there even when `CLAUDE_CODE_PLUGIN_CACHE_DIR` is set. What is inside that folder is not documented as of 2026-11-20. ([source](https://code.claude.com/docs/en/plugins/loading))
- Not copied into the cache: a `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS` plugin, a plugin folder with `.claude-plugin/plugin.json` saved under `~/.claude/skills/` or `.claude/skills/`, and a relative-path plugin in a marketplace added from a local path; these load from where they are. `marketplaces/<name>/` holds a whole marketplace's clone, plugins you did not install included. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins/loading))
- Observed with Claude Code 2.1.332 on 2026-11-26, in a throwaway config folder ([docs/trials.md](trials.md#run-11-a-domain-as-a-claude-code-plugin-in-a-local-marketplace-2026-11-26), run 11): a relative-path plugin from a marketplace added from a local folder was copied into `cache/<marketplace>/<plugin>/<version>/` as well, one folder per installed version, against the line above; after an update and an uninstall each old folder got `.orphaned_at`. Which folder a session reads was not tested.
- After an update or an uninstall, the previous version's folder gets an `.orphaned_at` marker and is removed 14 days later. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins/loading))
- A plugin skill loads as `/<plugin>:<skill>`. With a personal or project skill of the same name, "Both load, because plugin skills are namespaced", so two skills answer the same request. (checked 2026-11-20, [source](https://code.claude.com/docs/en/skills))
- Agents too: Claude Code "namespaces every component" under the plugin's name, "so an agent `reviewer` in plugin `deploy-tools` appears as `deploy-tools:reviewer`". A skill that starts an agent by its bare name does not reach a plugin's copy. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins-reference))
- `claude plugin list --json` prints "an array with one object per installation", each with `id` (`name@marketplace`, or `name@synced`, `name@inline`, `name@skills-dir`), `scope`, `enabled` ("Whether the plugin is enabled in your merged settings") and `installPath` ("Directory the plugin loads from"); a plugin loaded in place from its marketplace's folder has `readFromFolder`, "the plugin's source directory inside that folder", and a `project` or `local` install has `projectPath`. (checked 2026-11-20, [source](https://code.claude.com/docs/en/plugins/cli-reference))
- Observed with Claude Code 2.1.329 on 2026-11-20, in a throwaway config folder: `enabled` is worked out for the folder the command runs in. A plugin installed with `--scope project` for one repository showed `"enabled": true` there and `"enabled": false` in another repository; a user-scope plugin showed `true` in both. `installPath` named the current version's folder under `cache/`, and for a plugin from a marketplace added from a local folder, `readFromFolder` named the folder in that marketplace. The cards' plugin check therefore reads this list, run from the project folder, instead of searching the plugin folders, which also hold old versions, disabled plugins and other repositories' installs.
- Before a plugin is installed, Claude Code shows what it adds: "A plugin can run hooks and MCP servers, so read the pane before you install." "Whatever the tier, a plugin you install can run code with your user privileges." (read 2026-11-26, [source](https://code.claude.com/docs/en/discover-plugins), [source](https://code.claude.com/docs/en/plugins))
- An automatic scan of a skill's or a plugin's content before it loads: not documented as of 2026-11-26; searched [Security](https://code.claude.com/docs/en/security), [Plugins](https://code.claude.com/docs/en/plugins) and [Discover plugins](https://code.claude.com/docs/en/discover-plugins), which ask you to review a plugin yourself.

## Claude Code: MCP servers

- A remote server is added with `claude mcp add --transport http <name> <url>`, for example `claude mcp add --transport http notion https://mcp.notion.com/mcp`; a token goes in a header, `--header "Authorization: Bearer your-token"` (short forms `-t`, `-H`). (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- A local server is added with `claude mcp add [options] <name> -- <command> [args...]`, for example `claude mcp add --env AIRTABLE_API_KEY=YOUR_KEY --transport stdio airtable -- npx -y airtable-mcp-server`; everything after `--` goes to the server unchanged. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- `claude mcp list` shows each server's state (connected, needs authentication, failed), `claude mcp get <name>` one server, and `/mcp` the same inside a session. `claude mcp remove <name>` removes a server; for a remote one, `claude mcp logout <name>` first revokes its stored sign-in, which removing alone does not. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- Scopes: **local** (the default) loads in the current project and is private to you; **project** loads in the current project and is shared through version control; **user** loads in all your projects. Local and user servers are stored in `~/.claude.json`, project servers in `.mcp.json` at the project root (`--scope project`). When two share a name, local wins over project, project over user, user over plugins, plugins over claude.ai connectors. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- The docs say to check `.mcp.json` into version control so a team gets the same servers, and to keep machine-specific paths and secrets out of it by referring to variables: `${VAR}` and `${VAR:-default}` expand in a server's command, arguments, environment, URL and headers, for example `"Authorization": "Bearer ${API_KEY}"`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- Secrets reach a local server through `--env` / `-e KEY=value`, and a remote one through `--header`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- Trust: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." An interactive session asks before it uses a project's servers (`claude mcp reset-project-choices` resets the answers); `claude -p` loads them without asking. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- On Team and Enterprise plans, the MCP page says only admins can add servers; the claude.ai connector pages say an Owner adds a connector for the organization. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp), [source](https://claude.com/docs/connectors/getting-started))
- Signing in to a remote server: run `/mcp` in a session, "Then follow the steps in your browser to log in"; if the browser does not open, copy the URL Claude Code shows. From a terminal, `claude mcp login <name>`. A `claude -p` run cannot sign in, so sign in from an interactive session first. Tokens "are stored securely and refreshed automatically", and "Clear authentication" in the `/mcp` menu revokes access. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))
- Where a value typed after `--env` or `--header` ends up: not stated outright on the MCP page as of 2026-11-02. Local and user servers are stored in `~/.claude.json` (above), and the page says Claude Code checks "the values and key names under `env` and `headers`" of a server's configuration and "uses the values exactly as written". The kit therefore treats such a value, or one the shell fills in from `"$NAME"`, as written into `~/.claude.json` in plain text. ([source](https://code.claude.com/docs/en/mcp), [source](https://code.claude.com/docs/en/settings))
- A `${VAR}` reference also works for local and user servers, not only in `.mcp.json`: the page names "a local- or user-scoped server entry in `~/.claude.json`", and for "a server in the local, project, or user scope", `/mcp`, `claude mcp list` and `claude mcp get` "show a `${VAR}` reference by name rather than as its resolved value". None of the page's `claude mcp add` examples passes a reference; `claude mcp add-json <name> '<json>'` takes a server entry as JSON in single quotes, and `--scope user` puts it in your user configuration. In a remote server's `url` and `headers`, credential variables of Claude Code and your environment, such as `ANTHROPIC_API_KEY`, `HTTPS_PROXY` and `NPM_TOKEN`, "read as empty" instead of expanding. (checked 2026-11-02, [source](https://code.claude.com/docs/en/mcp))

The page lists what shell mode does (it adds the command and its output to the conversation, shows progress, and can go to the background with `Ctrl+B`) and says nothing about input. - `.claude/settings.local.json` holds your settings for one project. Claude Code keeps it out of git when it creates the file itself (through a global git excludes entry); a hand-made one must be added to `.gitignore`. (checked 2026-11-02, [source](https://code.claude.com/docs/en/settings))

## Claude Code: hooks

- A hook is configured under the `hooks` key of a settings file, by event, then a matcher group, then a list of handlers, for example `"PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "..." } ] } ]`. The files: `~/.claude/settings.json` (all your projects), `.claude/settings.json` (one project, can be committed), `.claude/settings.local.json` (one project, kept out of git when Claude Code writes it). (checked 2026-11-02, [source](https://code.claude.com/docs/en/hooks-guide))
- `Stop` runs "when the main Claude Code agent has finished responding", not after an interrupt by the user. A Stop hook that exits 2 "prevents Claude from stopping, continues the conversation", and Claude receives its stderr as the reason. Its input carries `stop_hook_active`, "`true` when Claude Code is already continuing as a result of a stop hook", so a hook can let the second stop through. (checked 2026-11-02, [source](https://code.claude.com/docs/en/hooks#stop))
- `SessionStart` runs "when a session begins or resumes", with the matchers `startup`, `resume`, `clear`, `compact` and `fork`. Claude Code "adds plain-text stdout as context that Claude can see and act on"; exit 2 there only shows stderr to the person. (checked 2026-11-02, [source](https://code.claude.com/docs/en/hooks-guide), [source](https://code.claude.com/docs/en/hooks))
- A `PreToolUse` hook that exits 2 blocks the tool call, and its stderr is the message Claude gets. A matcher of letters, digits and `|` is a list of exact tool names, so `Bash|PowerShell` covers both tools. (checked 2026-11-02, [source](https://code.claude.com/docs/en/hooks))
- A hook that exits with any code other than 0 or 2, "or fails in some other way, such as not starting or printing invalid JSON", is a non-blocking error: "The action goes ahead", unless its failure is set to block the action. "Exit code 1 without valid JSON output is a non-blocking error". So a PreToolUse guard that crashes, or whose script path is wrong, lets the command run. (read 2026-11-18, [source](https://code.claude.com/docs/en/hooks#exit-code-output))
- `"onFailure": "block"` on a `command` or `http` hook makes a failure or a timeout do "what exit code 2 does on that event"; the other value is `"continue"`. "Requires Claude Code v2.1.295 or later." It has no effect on `Stop`, `SubagentStop`, `TaskCompleted` and `TeammateIdle` hooks, or on hooks set to run in the background. (read 2026-11-18, [source](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails))
- Exec form: a command hook with `args` runs no shell. Claude Code "resolves `command` as an executable on `PATH` and spawns it directly with `args` as the argument vector", and path placeholders such as `${CLAUDE_PROJECT_DIR}` "are substituted into `command` and into each `args` element as plain strings"; `$` and quotes pass through as written. "Prefer exec form for any hook that references a path placeholder." For example `"command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/git-guardrails/block-dangerous-git.mjs"]`. On Windows, `command` must resolve to a real executable such as a `.exe`, not a `.cmd` or `.bat` shim. The page states no minimum Claude Code version for exec form (read 2026-11-18). ([source](https://code.claude.com/docs/en/hooks#exec-form-and-shell-form))
- Shell-form command hooks (no `args`) run through `sh -c` on macOS and Linux, and on Windows through Git Bash, or PowerShell when Git Bash is not installed. How a path inside `node "<path>"` is treated on Windows: not documented as of 2026-11-25; exec form (above) passes the path to `node` as one argument with no shell on any system, and the reference says to wrap each placeholder in double quotes in shell form (read 2026-11-18). ([source](https://code.claude.com/docs/en/hooks), [source](https://code.claude.com/docs/en/hooks#reference-scripts-by-path))
- In a shell-form hook that runs in PowerShell, `${CLAUDE_PROJECT_DIR}` and `$env:CLAUDE_PROJECT_DIR` work; the bare `$CLAUDE_PROJECT_DIR` does not: "PowerShell parses it as an undefined local variable and resolves it to `$null`, which leaves the script path without its project-root prefix." (read 2026-11-18, [source](https://code.claude.com/docs/en/hooks#reference-scripts-by-path-in-powershell-hooks))
- `/hooks` opens a read-only list of the configured hooks, each labelled with where it comes from. (checked 2026-11-02, [source](https://code.claude.com/docs/en/hooks-guide))
- `Stop` takes no matcher: the reference lists it among the events with "no matcher support", which "always fires on every occurrence", and "If you add a matcher field to an event without matcher support, it is silently ignored." (read 2026-11-25, [source](https://code.claude.com/docs/en/hooks))

## Claude Code: permission rules for secret files

Checked on 2026-11-09, and run once on Windows with Claude Code 2.1.319 in a throwaway folder: `claude -p` reading only that folder's settings (`--setting-sources project`), with the deny rules of [the sensitive-file deny rules card](../cards/sensitive-file-deny-rules.md) and a made-up value in each file. Run again on 2026-11-10 on Windows (2.1.319) and on macOS (2.1.321); the last three items below hold those results.

- A permission rule is `Tool` or `Tool(specifier)`, listed under `permissions.allow`, `permissions.ask` or `permissions.deny` in a settings file. "Permission rules are enforced by Claude Code, not by the model": instructions in a prompt or a `CLAUDE.md` "shape what Claude tries to do, but they don't change what Claude Code allows." (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#manage-permissions))
- Rules are checked in the order deny, ask, allow, and the first match decides; "An allow rule can't carve an exception out of a deny rule." A tool denied at any level cannot be allowed by another, and a list such as `permissions.deny` set in several files is combined, not replaced. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#settings-precedence), [source](https://code.claude.com/docs/en/settings#lists-merge-instead-of-overriding))
- The files: `~/.claude/settings.json`, for you in every project (`%USERPROFILE%\.claude` on Windows; `CLAUDE_CONFIG_DIR` moves the folder); `.claude/settings.json`, shared with everyone in a project once committed; `.claude/settings.local.json`, for you in one project; and managed settings from an organization. Settings files are strict JSON: "a `//` comment or a trailing comma is a syntax error". (checked 2026-11-09, [source](https://code.claude.com/docs/en/settings))
- `deny` and `ask` rules in a project's `.claude/settings.json` apply at once; its `allow` rules wait until you accept the workspace trust dialog. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#project-allow-rules-and-workspace-trust))
- An organization's managed settings can set `allowManagedPermissionRulesOnly`, which "makes managed settings the only settings source of permission rules". (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#managed-settings))
- The settings page's own example stops Claude Code reading `.env` files from `~/.claude/settings.json` with `"deny": ["Read(./.env)", "Read(./.env.*)"]`. (checked 2026-11-09, [source](https://code.claude.com/docs/en/settings#edit-a-settings-file))
- `Read` and `Edit` rules use gitignore pattern syntax. `//path` is an absolute path from the filesystem root; `~/path` starts at your home folder; `/path` starts at the settings source, which for `~/.claude/settings.json` is `~/.claude`, not the project; `path` or `./path` starts at the current folder. A bare file name matches at any depth below the current folder, and `Read(//**/.env)` blocks "any `.env` anywhere on the filesystem". On Windows a path is turned into POSIX form before matching (a path on `C:\` starts `/c/`), and `//**/.env` matches on every drive. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#how-path-patterns-match))
- A rule that starts with `!` carves paths out of the rules listed before it in the same file, but only out of `path` or `./path` rules: it "can't reach a rule anchored with" `/`, `~/` or `//`. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#read-and-edit))
- What a `Read` deny rule covers: the Read tool; "a best-effort attempt" for the other built-in tools that read files, such as Grep and Glob; `@file` mentions and the context a connected IDE shares; pasted image paths and directory listings, from v2.1.290. It also blocks Edit and Write on the same path, creating a new file there included (Write from v2.1.228), but not NotebookEdit. The settings reference sums it up: Claude Code "excludes matching files from file discovery and search results, denies reads of them, and blocks the Edit and Write tools on the matching paths." (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#read-and-edit), [source](https://code.claude.com/docs/en/settings-reference#permissions-deny))
- In the shell, `Read` and `Edit` deny rules "apply to Claude's built-in file tools, to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and `tee`, and to the targets of Bash redirections" (input redirects such as `< file` from v2.1.257). "They don't apply to a command that reads files without naming them, such as `grep -r pattern .` run from the directory that holds the file, or to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself." (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#read-and-edit), [source](https://code.claude.com/docs/en/settings-reference#permissions-deny))
- `cat`, `head`, `grep` and `find` are among the read-only commands that run without a permission prompt in every mode. On macOS, Linux and WSL, Claude Code leaves the Glob and Grep tools out by default, and Claude searches with `find` and `grep` through Bash; "In Claude's shell those two commands run embedded versions of `bfs` and `ugrep`". (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#read-only-commands), [source](https://code.claude.com/docs/en/tools-reference#glob-tool-behavior))
- Whether `Read` deny rules apply to PowerShell commands: not documented as of 2026-11-25; the PowerShell section covers command rules only. ([source](https://code.claude.com/docs/en/permissions#powershell))
- MCP tools are matched by name: `mcp__<server>__<tool>` for one tool, `mcp__<server>__*` for all of a server's. The `Read` rules' list of what they cover names built-in tools and no MCP tool, and "When Claude Code loads a settings file, it skips any `mcp__` rule that has parentheses", so a settings file can deny an MCP tool only as a whole, not for one path. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#mcp), [source](https://code.claude.com/docs/en/permissions#match-by-input-parameter), [source](https://code.claude.com/docs/en/permissions#read-and-edit))
- A mod (code a plugin runs inside Claude Code) that approves tool calls "can approve a call that a deny rule refuses" in a session with neither managed settings nor a Team or Enterprise `/login`. (checked 2026-11-09, [source](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks))
- For a limit that holds for every program a shell command starts, the docs point to the sandbox. It "runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed." It covers shell commands only, and `Read` and `Edit` deny rules are merged into its configuration. (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing), [source](https://code.claude.com/docs/en/sandboxing#permission-rules))
- `/permissions` lists every rule and the settings file it comes from, and you can add or remove a rule there; "A rule you add through `/permissions` follows the row for the settings file you save it to", so it is saved to the file you pick. The dialog's steps are not documented as of 2026-11-25. A malformed rule raises a Settings Warning and is skipped while the rest of the file stays in effect, and `claude doctor` lists the entries Claude Code rejected. Claude Code reloads a settings file when it changes, permission edits included, without a restart. ([source](https://code.claude.com/docs/en/permissions#manage-permissions), [source](https://code.claude.com/docs/en/permissions#how-path-patterns-match), [source](https://code.claude.com/docs/en/settings#fix-a-broken-settings-file), [source](https://code.claude.com/docs/en/settings#when-edits-take-effect))

## Claude Code: the sandbox

Checked on 2026-11-09. The kit does not set the sandbox up; these facts say what it would add. ([source](https://code.claude.com/docs/en/sandboxing))

- The sandbox is "a boundary that the operating system enforces around the shell commands Claude runs on your machine": its limits apply to Bash, PowerShell and Monitor commands "and the processes they start". It "covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it", and a `denyRead` entry "doesn't stop the Read tool". (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing))
- "The sandbox runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed." It is off by default; `/sandbox` in a session or `sandbox.enabled: true` in a settings file turns it on. (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts))
- Network: a sandboxed command has "No direct route out. Connections go through a proxy on your machine that checks each host against your allowed domains, which start empty", set with `sandbox.network.allowedDomains`; your permission mode decides what happens to other hosts, and `sandbox.network.strictAllowlist`, set in user, managed or `--settings` settings, refuses them without asking. `allowedDomains` "doesn't limit WebFetch", which follows permission rules instead. (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts), [source](https://code.claude.com/docs/en/sandboxing#hosts-outside-your-allowed-domains))
- Files: by default a sandboxed command can read "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`"; `sandbox.filesystem.denyRead` narrows that. (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts))
- What still runs outside it: a command you type after `!` in most sessions, commands listed in `excludedCommands`, and a command Claude asks to run unsandboxed after it fails in the sandbox. (checked 2026-11-09, [source](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox))

## Claude Code: worktrees and background commands

- Claude Code makes worktrees itself. `claude --worktree <name>` (`-w`) starts a session in one: "By default, the worktree is created under .claude/worktrees/<name>/ at your repository root, on a new branch named worktree-<name>". Asked in a session to "work in a worktree", Claude "creates one with the EnterWorktree tool". Its defaults: "it creates them under .claude/worktrees/, branches them from your repository's default branch, and checks out only tracked files"; the `worktree.baseRef` setting `"head"` branches from the current local `HEAD` instead. - A background shell command belongs to its session: "Background tasks are automatically cleaned up when Claude Code exits." Claude Code also stops one when its output passes 5 GB ("automatically terminated if output exceeds 5GB"); on macOS and Linux under "critical memory pressure", once the session "has been idle for at least 30 minutes"; at a time limit "In a session that runs unattended, such as a -p run or a cloud session" (a local session you work in has none); and "A background command that a foreground subagent started ends when that subagent's run ends". "If you background the session instead of exiting it, your background tasks keep running in the background session." (read 2026-11-25, [source](https://code.claude.com/docs/en/interactive-mode), [source](https://code.claude.com/docs/en/tools-reference))

## GitHub: merge methods

- A repository's `allow_merge_commit`, `allow_squash_merge` and `allow_rebase_merge` are read with `GET /repos/{owner}/{repo}` and changed with `PATCH /repos/{owner}/{repo}`, each "true to allow ... or false to prevent" that method. (read 2026-11-25, [source](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28#update-a-repository))
- Who may change those settings: on the web, "Configure pull request merges" is allowed for the Maintain and Admin roles of an organization's repository, not for Read, Triage, Moderate or Write. "Repositories owned by personal accounts have a single owner who has full control of the repository." Through the API, "The fine-grained token must have the following permission set: "Administration" repository permissions (write)" for "Update a repository". (read 2026-11-25, [source](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization), [source](https://docs.github.com/en/account-and-profile/reference/permission-levels-for-a-personal-account-repository), [source](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28#update-a-repository))
- With the `gh` command line: `gh api repos/{owner}/{repo} --jq '.allow_merge_commit, .allow_squash_merge, .allow_rebase_merge'` reads them, and `gh api -X PATCH repos/{owner}/{repo} -F allow_squash_merge=false -F allow_rebase_merge=false` changes them; `-F` sends `true` and `false` as real booleans, where `-f` would send text. The placeholders `{owner}` and `{repo}` "will get replaced with values from the repository of the current directory or the repository specified in the GH_REPO environment variable", so outside the repository's folder, name it (`repos/<owner>/<repo>`). (read 2026-11-25, [source](https://cli.github.com/manual/gh_api))
- On the web: the repository's Settings, "General", the "Pull Requests" section. (checked 2026-11-02, [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests))
- `gh pr merge` takes `--merge` ("Merge the commits with the base branch"), `--squash` or `--rebase`. What it does when the chosen method is switched off on the repository: not documented as of 2026-11-25; searched [gh pr merge](https://cli.github.com/manual/gh_pr_merge), [About merge methods on GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github). The second page says "To squash and merge pull requests, you must have write permissions in the repository, and the repository must allow squash merging."
- A rebase merge on GitHub "Always updates the committer information and creates new commit SHAs", and with **Rebase and merge** "the commits in the head branch are added to the base branch without commit signature verification": GitHub creates a modified commit and "can't sign the commit on the user's behalf". The documented workaround is to rebase and merge locally, then push. (checked 2026-11-02, [source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github), [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification))
- `gh` "is supported for users on GitHub.com, GitHub Enterprise Cloud, and supported GitHub Enterprise Server versions"; its README names no other host. ## Git: signed commits and identity per folder

Checked on 2026-11-02, and run once on Windows with git 2.54.0 in a throwaway folder (a temporary key and `GIT_CONFIG_GLOBAL` pointing at a temporary file).

- SSH signing came with git 2.34: "In addition to GnuPG, ssh public crypto can be used for object and push-cert signing." `gpg.format` takes `openpgp` (the default), `x509` or `ssh`. (checked 2026-11-02, [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc), [source](https://git-scm.com/docs/git-config))
- GitHub shows a commit as Verified when its signature checks out "against a public key you have added to your account"; "SSH signature verification is available in Git 2.34 or later." (checked 2026-11-02, [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification))
- An SSH key goes on GitHub as one of two types, "either authentication or signing". To sign with the key you already push with, upload it again as a signing key: `gh ssh-key add <key>.pub --type signing`. GPG keys: `gh gpg-key add`. Both have `delete`; on the web, Settings, then "SSH and GPG keys". (checked 2026-11-02, [source](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account), [source](https://cli.github.com/manual/gh_ssh-key_add), [source](https://cli.github.com/manual/gh_gpg-key))
- Making a key, as GitHub's pages give it: `ssh-keygen -t ed25519 -C "your_email@example.com"`, which asks for a passphrase twice; `gpg --full-generate-key` (GnuPG 2.1.17 or later); and `gpg --armor --export <key ID>` prints a GPG public key to paste into GitHub. (checked 2026-11-02, [source](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent), [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/generating-a-new-gpg-key))
- Telling git which key to use: for SSH, `git config --global gpg.format ssh` and `git config --global user.signingkey /PATH/TO/.SSH/KEY.PUB`; for GPG, `git config --global user.signingkey <key ID>`. `git config --global commit.gpgsign true` signs every commit. With `gpg.format` set to `ssh`, `user.signingKey` "can contain the path to either your private ssh key or the public key when ssh-agent is used"; `commit.gpgSign` is "A boolean to specify whether all commits should be GPG signed". (checked 2026-11-02, [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key), [source](https://git-scm.com/docs/git-config))
- An allowed-signers line holds "principals, options, keytype, base64-encoded key"; the option `namespaces="..."` "Specifies a pattern-list of namespaces that are accepted for this key", and the namespace in the signature must match. Git's SSH commit signatures carry the namespace `git` (the Windows run printed `Good "git" signature`), so `namespaces="git"` accepts the key for git signatures only. The file "can be set to a location outside of the repository and every developer maintains their own trust store." (checked 2026-11-02, [source](https://man.openbsd.org/ssh-keygen.1), [source](https://git-scm.com/docs/git-config))
- A GPG key is matched to "your committer identity and your verified email address". Whether an SSH signing key needs the commit email to match: not documented as of 2026-11-25; searched [Telling Git about your signing key](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key), [About commit signature verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification), [Displaying verification statuses for all of your commits](https://docs.github.com/en/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits).
- Checking an SSH signature on your own machine needs `gpg.ssh.allowedSignersFile`: a file of lines, each the principals (an email address), then the public key. Without it git prints `error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification` and `No signature`. With it, `git log --show-signature -1` printed `Good "git" signature for <email> with ED25519 key SHA256:...` in the Windows run. (checked 2026-11-02, [source](https://git-scm.com/docs/git-config), [source](https://man.openbsd.org/ssh-keygen.1))
- For a GPG-signed commit, `git log --show-signature -1` printed `gpg: Good signature from "<name> <email>"` in the Windows run (GnuPG 2.4.9). (checked 2026-11-02, [source](https://git-scm.com/docs/git-log))
- A passphrase you type is kept by the GnuPG agent for `default-cache-ttl` seconds after its last use, and never longer than `max-cache-ttl`: 600 and 7,200 by default, as `gpgconf --list-options gpg-agent` printed on GnuPG 2.4.9. Both go in `gpg-agent.conf` in the GnuPG home folder. (checked 2026-11-02, [source](https://www.gnupg.org/documentation/manuals/gnupg/Agent-Options.html))
- On Windows, with `GNUPGHOME` set in Git Bash, git's signing call did not find the key in the probe: the folder reached GnuPG as a drive-letter path such as `X:/...`, which it read as relative. Passing `--homedir` through a small `gpg.program` script worked. Not documented as of 2026-11-26; searched [GnuPG: configuration files](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Configuration.html) and [GnuPG: esoteric options](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Esoteric-Options.html), which describe `--homedir` and `GNUPGHOME` but not a drive-letter path set in Git Bash.
- One identity per folder: `includeIf "gitdir:<folder>/"` includes another config file for every repository under that folder; a pattern ending in `/` matches the folder and everything inside it, and `gitdir/i` matches without regard to case. The docs show forward slashes and say nothing of drive letters; in the Windows run, `gitdir:X:/work/`-style patterns (a drive letter, then forward slashes) worked, and `gitdir/i` matched the same drive letter in lower case. The run added each include from the command line, without opening the config file: `git config --global includeIf."gitdir:<folder>/".path <file>` (there with `--file` on a temporary config). (checked 2026-11-02, [source](https://git-scm.com/docs/git-config#_conditional_includes))
- Conditional includes came with git 2.13: "The configuration file learned a new "includeIf.<condition>.path" that includes the contents of the given path only when the condition holds." Git's config documentation at v2.13.0 has `includeIf` with `gitdir` and `gitdir/i`, and "If the pattern ends with /, ** will be automatically added"; at v2.12.0 it has no `includeIf`. (read 2026-11-25, [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.13.0.adoc), [source](https://github.com/git/git/blob/v2.13.0/Documentation/config.txt), [source](https://github.com/git/git/blob/v2.12.0/Documentation/config.txt))
- `GIT_CONFIG_GLOBAL` (git 2.32) makes git read the given file instead of your global config; `GIT_CONFIG_NOSYSTEM` skips the system config; `GNUPGHOME` moves GnuPG's home folder, `~/.gnupg` by default. The kit's trial runs under all three so it never touches a real setup. (checked 2026-11-02, [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.32.0.adoc), [source](https://git-scm.com/docs/git-config#ENVIRONMENT), [source](https://www.gnupg.org/documentation/manuals/gnupg/Invoking-gpgconf.html))
- To undo a setting, `git config unset <key>` (newer git) or `git config --unset <key>`, which the docs now list as deprecated, in the same scope (`--global`, or inside the repository for a local one). (checked 2026-11-02, [source](https://git-scm.com/docs/git-config))
- `git config --name-only`: "Output only the names of config variables for list or get." The page for git 2.12.5 says "for --list or --get-regexp"; the current page lists `--get-regexp` as a deprecated mode, "Replaced by git config get --all --show-names --regexp <name-regexp>". Seen with git 2.54.0 on Windows on 2026-11-25, in a throwaway repository: `git config --local --name-only --get-regexp '^(commit\.gpgsign|gpg\.format|user\.signingkey)$'` printed `commit.gpgsign` and `gpg.format`, without values. (read 2026-11-25, [source](https://git-scm.com/docs/git-config), [source](https://git-scm.com/docs/git-config/2.12.5))
- Where GnuPG comes from: on Windows, Git for Windows carries a `gpg.exe` in its `usr\bin` folder (GnuPG 2.4.9 with git 2.54.0; not stated on its site), or Gpg4win installs it on its own; on macOS, `brew install gnupg`; on Debian and Ubuntu, `sudo apt install gnupg`. (checked 2026-11-02, [source](https://gpg4win.org/about.html), [source](https://formulae.brew.sh/formula/gnupg), [source](https://packages.debian.org/stable/gnupg))
- Windows 10 build 1809 and later offers OpenSSH, `ssh-keygen` included, as an optional feature; Git for Windows brings its own (OpenSSH 10.3 with git 2.54.0). (checked 2026-11-02, [source](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-overview))

## Git: hooks and worktrees

- "By default the hooks directory is `$GIT_DIR/hooks`" (`.git/hooks` in a normal repository). `core.hooksPath` moves it: "Git will try to find your hooks in that directory ... instead of in `$GIT_DIR/hooks`", so while it is set, hooks left in `.git/hooks` do not run. The path can be absolute or relative. (checked 2026-11-02, [source](https://git-scm.com/docs/githooks), [source](https://git-scm.com/docs/git-config))
- Setting `core.hooksPath` to `/dev/null` turns every hook off, the docs suggest for one command at a time: `git -c core.hooksPath=/dev/null ...`. (checked 2026-11-02, [source](https://git-scm.com/docs/git-config))
- A setting can also come from the environment: "If GIT_CONFIG_COUNT is set to a positive number, all environment pairs GIT_CONFIG_KEY_<n> and GIT_CONFIG_VALUE_<n> up to that number will be added to the process's runtime configuration." So `core.hooksPath` can be set for one command with no `-c` and no `git config`. (checked 2026-11-09, [source](https://git-scm.com/docs/git-config#ENVIRONMENT))
- Config can also come from files the command does not name: `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` "Take the configuration from the given files instead from global or system-level configuration files", and "You can include a config file from another by setting the special `include.path` (or `includeIf.*.path`) variable to the name of the file to be included." `GIT_CONFIG_PARAMETERS`, which `git-guardrails` names among its known gaps, is described on neither page (checked 2026-11-10). ([source](https://git-scm.com/docs/git), [source](https://git-scm.com/docs/git-config))
- Long options can be shortened: "Commands that support the enhanced option parser accepts unique prefix of a long option as if it is fully spelled out", for example "git commit --amen behaves as if you typed git commit --amend". Which prefix is unique depends on the command's other options. (checked 2026-11-09, [source](https://git-scm.com/docs/gitcli))
- `git am` runs the `pre-applypatch` and `applypatch-msg` hooks by default: "Skip these hooks with `-n` or `--no-verify`." Its page lists no `--verbose` and no other long option that starts with `v`, so on `git am` even `--no-v` is a unique prefix of `--no-verify` (checked 2026-11-10). ([source](https://git-scm.com/docs/git-am), [source](https://git-scm.com/docs/gitcli))
- `pre-commit` runs before the commit is made; "Exiting with a non-zero status from this script causes the `git commit` command to abort before creating a commit", and `git commit --no-verify` bypasses it. (checked 2026-11-02, [source](https://git-scm.com/docs/githooks))
- `pre-push` "is called by git-push[1] and can be used to prevent a push from taking place"; "If this hook exits with a non-zero status, git push will abort without pushing anything." (read 2026-11-25, [source](https://git-scm.com/docs/githooks))
- How Git for Windows runs a hook that is an sh script: not documented as of 2026-11-25; searched [githooks](https://git-scm.com/docs/githooks), [Git for Windows FAQ](https://github.com/git-for-windows/git/wiki/FAQ), [Git for Windows release notes](https://github.com/git-for-windows/build-extra/blob/main/ReleaseNotes.md), [gitforwindows.org](https://gitforwindows.org/).
- `git mv` moves or renames a file, a folder or a symlink and updates the index, "but the change must still be committed". `git log --follow <file>` will "Continue listing the history of a file beyond renames (works only for a single file)". (checked 2026-11-02, [source](https://git-scm.com/docs/git-mv), [source](https://git-scm.com/docs/git-log))
- `git worktree add -b <new-branch> <path> <commit-ish>` creates a worktree at `<path>` with a new branch "starting at `<commit-ish>`" (`HEAD` when left out); "By default, `-b` refuses to create a new branch if it already exists." (checked 2026-11-02, [source](https://git-scm.com/docs/git-worktree))
- `git worktree remove <worktree>`: "Only clean worktrees (no untracked files and no modification in tracked files) can be removed"; `--force` removes an unclean one, and "The main worktree cannot be removed." `git worktree prune` removes the records of worktrees whose folders are gone; `git worktree list` lists the main worktree first, then the linked ones. (checked 2026-11-02, [source](https://git-scm.com/docs/git-worktree))
- `git worktree`, by git's release notes and its documentation at each release tag. It came with git 2.5: the release notes call it "A replacement for contrib/workdir/git-new-workdir" and say "Consider this as still an experimental feature; its UI is still likely to change." The v2.5.0 documentation lists `git worktree add` and `git worktree prune`. Git 2.7: ""git worktree" learned a "list" subcommand." `add`'s `--[no-]track` is first in the documentation at v2.16.0, not at v2.15.0. `git worktree move` and `git worktree remove [--force]` are first at v2.17.0. (read 2026-11-25, [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.5.0.adoc), [source](https://github.com/git/git/blob/v2.5.0/Documentation/git-worktree.txt), [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.7.0.adoc), [source](https://github.com/git/git/blob/v2.15.0/Documentation/git-worktree.txt), [source](https://github.com/git/git/blob/v2.16.0/Documentation/git-worktree.txt), [source](https://github.com/git/git/blob/v2.17.0/Documentation/git-worktree.txt))
- The other git features that the worktree cards and the `using-git-worktrees` skill run, by the same two kinds of page. Git 2.22: ""git branch" learned a new subcommand "--show-current"." `git init -b <branch-name>` (`--initial-branch`) is first in the documentation at v2.28.0, not at v2.27.0. `git rev-parse --show-superproject-working-tree` is first at v2.13.0, and `--git-common-dir` is in the v2.5.0 documentation. So the worktree steps need git 2.17, the skill needs 2.22, and the cards' checks, which make a throwaway repository with `git init -b`, need 2.28. (read 2026-11-25, [source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.22.0.adoc), [source](https://github.com/git/git/blob/v2.27.0/Documentation/git-init.txt), [source](https://github.com/git/git/blob/v2.28.0/Documentation/git-init.txt), [source](https://github.com/git/git/blob/v2.13.0/Documentation/git-rev-parse.txt), [source](https://github.com/git/git/blob/v2.5.0/Documentation/git-rev-parse.txt), [source](https://github.com/git/git/blob/master/Documentation/RelNotes/1.8.5.adoc), [source](https://github.com/git/git/blob/master/Documentation/RelNotes/1.8.2.adoc), [source](https://github.com/git/git/blob/master/Documentation/RelNotes/1.7.2.adoc))
- `git worktree add -b <new-branch> <path> <remote>/<branch>` gives the new branch an upstream unless `--no-track` is passed. `--track`: "When creating a new branch, if <commit-ish> is a branch, mark it as "upstream" from the new branch. This is the default if <commit-ish> is a remote-tracking branch." For `git branch`, `branch.autoSetupMerge` decides when neither option is given: "The default option, `true`, behaves as though `--track=direct` were given whenever the start-point is a remote-tracking branch", and `--no-track` means "Do not set up "upstream" configuration, even if the `branch.autoSetupMerge` configuration variable is set." Seen with git 2.54.0: without `--no-track`, `worktree add` prints "branch '<new-branch>' set up to track 'origin/main'." and `git status -sb` shows `## <new-branch>...origin/main`; with it, `## <new-branch>` (checked 2026-11-18). ([source](https://git-scm.com/docs/git-worktree), [source](https://git-scm.com/docs/git-branch))
- A remote's default branch is the symbolic ref `refs/remotes/<name>/HEAD`, and "Having a default branch for a remote is not required". With `git remote set-head <name> -a`, "the remote is queried to determine its HEAD", and the ref is set to the same branch. With `fetch.followRemoteHEAD` at its default, `create`, a fetch will "Create remotes/<name>/HEAD if a ref exists on the remote, but not locally. An existing symbolic-ref will not be touched." `git symbolic-ref --short <name>` prints where the ref points, shortened "e.g. from refs/heads/master to master", and exits "with status 1 if the requested name is not a symbolic ref, or 128 if another error occurs". (read 2026-11-25, [source](https://git-scm.com/docs/git-remote), [source](https://git-scm.com/docs/git-config), [source](https://git-scm.com/docs/git-symbolic-ref))
- `git worktree remove` deletes a worktree's ignored files, and plain `git status --porcelain` does not list them. The worktree page counts a worktree as clean with "no untracked files and no modification in tracked files" and says nothing of ignored files; the status page says "Ignored files are not listed unless `--ignored` is used; if it is, ignored files are indicated by `!!`." ([source](https://git-scm.com/docs/git-worktree), [source](https://git-scm.com/docs/git-status))
- `git clean` "Cleans the working tree by recursively removing files that are not under version control": "Normally, only files unknown to Git are removed, but if the -x option is specified, ignored files are also removed", and `-X` will "Remove only files ignored by Git". Without `-d` it "will not recurse into untracked directories" (unless a path is given); it removes nothing without `-f` "If the Git configuration variable clean.requireForce is not set to false"; and `-n` (`--dry-run`) removes nothing and will "show what would be done". (read 2026-11-25, [source](https://git-scm.com/docs/git-clean))
- `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` take, among other forms, the "Git internal format": "It is <unix-timestamp> <time-zone-offset>, where <unix-timestamp> is the number of seconds since the UNIX epoch". ## Git: line endings

- When a path's `text` attribute is unspecified, "Git uses the core.autocrlf configuration variable to determine if the file should be converted". `core.autocrlf` set to "true" "is the same as setting the text attribute to "auto" on all files and core.eol to "crlf"", for "CRLF line endings in your working directory" while the repository has LF. "Unsetting the text attribute on a path tells Git not to attempt any end-of-line conversion upon checkin or checkout": a line `<pattern> -text` in `.gitattributes`. `git config --show-origin --get core.autocrlf` prints the value in force and the file it comes from. Docker Engine without Desktop, on Ubuntu: `sudo apt purge docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin docker-ce-rootless-extras`; "Images, containers, volumes, or custom configuration files on your host aren't automatically removed" (`sudo rm -rf /var/lib/docker` and `sudo rm -rf /var/lib/containerd` delete them). (read 2026-11-25, [source](https://docs.docker.com/desktop/uninstall/), [source](https://docs.docker.com/engine/install/ubuntu/))
- Docker Desktop is licensed under the Docker Subscription Service Agreement. It is free for "Small businesses (fewer than 250 employees AND less than $10 million in annual revenue)", personal use, education and non-commercial open source projects, and "requires a paid subscription for" "Professional use in larger organizations", "Government entities" and "Commercial use beyond the free tier limits". "The licensing and distribution terms for Docker and Moby open-source projects, such as Docker Engine, aren't changing." (read 2026-11-25, [source](https://docs.docker.com/subscription/desktop-license/))

## claude.ai: Projects

- A Project holds its own instructions and a knowledge base of uploaded documents, text, code or other files. (checked 2026-11-02, [source](https://support.claude.com/en/articles/9517075-what-are-projects))
- Each Project has its own memory. (checked 2026-11-02, [source](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work))
- The free plan allows at most five Projects. Project files: "File size: 30MB per file" and "Number of files: Unlimited, but total content must fit within Claude's context window"; chat uploads have their own limits (500MB per file, up to 20 files per chat). On a paid plan, RAG expands a Project's capacity "by up to 10x". The page names no other limit that differs by plan. (read 2026-11-25, [source](https://support.claude.com/en/articles/9517075-what-are-projects), [source](https://support.claude.com/en/articles/8241126-what-kinds-of-documents-can-i-upload-to-claude-ai), [source](https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects))
- How a Project's knowledge and instructions reach its chats: "Anything you upload to this space will be used across all of your chats within that project", and "Claude will use these instructions for all the chats within the project." On a paid plan (Pro, Max, Ultra, Team, Enterprise), "When your project knowledge approaches the context window limit, Claude will automatically enable RAG mode"; then, "Instead of loading all project content into memory at once, Claude intelligently searches and retrieves only the most relevant information needed to answer your questions." "When possible, projects will use in-context processing for optimal performance." (read 2026-11-25, [source](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects), [source](https://support.claude.com/en/articles/11473015-retrieval-augmented-generation-rag-for-projects))
- To make a Project: "Projects" in the left side (claude.ai/projects), then "+ New Project". Instructions: "Set project instructions", then "Save instructions". Knowledge: the "+" button in the project knowledge base, on the right side of the project's page. (read 2026-11-25, [source](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects))

## claude.ai: memory and past chats

- Memory is on by default on Free, Pro, Max and Ultra. On Team and Enterprise, owners control whether memory is available: "In most organizations created on or after October 31, 2026 (Pacific Time), memory starts on for each member unless they've turned it off before with the same account. In older organizations, it's off for each member until they turn it on." "Owners can't turn memory on for individual users." (checked 2026-11-25, [source](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work))
- To turn it on or off: Settings > Your Claude > "Generate memory from chats" (older layout: Settings > Memory). Turning it off offers "Pause memory", which keeps what was remembered but stops using and adding to it, or "Reset memory", which deletes everything, Project memories included. (checked 2026-11-25, [source](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work))
- What Claude remembers appears under "Topics", where you can edit or delete it; you can also tell Claude in a chat what to remember or forget. (checked 2026-11-02, [source](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work))
- Searching and referencing past chats: Pro, Max, Ultra, Team and Enterprise, not Free; on by default, with the toggle "Search and reference chats" under Settings > Your Claude. (checked 2026-11-02, [source](https://support.claude.com/en/articles/11817273-how-does-claude-s-memory-work))

## claude.ai: custom skills and the built-in document skills

- Custom skills are available on Free, Pro, Max, Ultra, Team and Enterprise and need code execution turned on; Team and Enterprise owners can turn skill creation off. (checked 2026-11-02, [source](https://support.claude.com/en/articles/12512180-using-skills-in-claude))

- To remove a custom skill you uploaded: Customize > Skills, click the skill to see its details, then "Use the toggle in the upper right corner to disable the skill"; "To delete the custom skill entirely, click the "..." button next to the toggle, then select "Delete"", and click "Delete" again in the confirmation prompt. - The built-in document skills work with Excel, Word, PowerPoint and PDF files. On Free, Pro, Max and Ultra, turn on Settings > Capabilities > "Code execution and file creation" ("Create and edit files" in the newer layout), then switch the skills on in Customize > Skills. On Team they are on for the organization by default; on Enterprise the owners set them in Organization settings > Plugins & skills > Policy. (checked 2026-11-02, [source](https://support.claude.com/en/articles/12512180-using-skills-in-claude))
- "Code execution and file creation" gives Claude "a sandboxed computing environment". There Claude "can create Python scripts for data analysis", processes "CSV, TSV, and other data files", and with network access installs packages "from approved package managers (npm, PyPI, etc.)"; on Free, Pro, Max and Ultra, "Network access is enabled, allowing Claude to install packages from approved sources". Uploads and downloads are limited to "30MB per file". Which languages besides Python the sandbox runs, and which packages it holds before any install: not documented as of 2026-11-25; searched [Create and edit files with Claude](https://support.claude.com/en/articles/12111783-create-and-edit-files-with-claude). (read 2026-11-25, [source](https://support.claude.com/en/articles/12111783-create-and-edit-files-with-claude))
- In claude.ai, the built-in skills the help page names are for Excel, Word, PowerPoint and PDF files; a `dataviz` skill among them: not documented as of 2026-11-25. ([source](https://support.claude.com/en/articles/12512180-using-skills-in-claude))

## Other agent tools: instruction files, skills and hooks

- OpenAI Codex: "Codex reads `AGENTS.md` files before doing any work." From the project root down to the working folder, it checks each folder for `AGENTS.override.md`, then `AGENTS.md`, then the names listed in `project_doc_fallback_filenames`, and "includes at most one file per directory"; `CLAUDE.md` is read only when that setting lists it. (read 2026-11-25, [source](https://developers.openai.com/codex/guides/agents-md.md))
- OpenAI Codex, skills: "A skill is a directory with a `SKILL.md` file plus optional scripts and references." In a repository it scans `.agents/skills` in each folder from the working folder up to the repository root; the page does not name `.claude/skills`. (read 2026-11-25, [source](https://developers.openai.com/codex/skills.md))
- OpenAI Codex, hooks: its own hooks use Claude Code's event names (`PreToolUse`, `Stop` and others) and the same nesting, in `.codex/hooks.json` or `config.toml`, and "Before a non-managed hook can run, Codex requires you to review and trust the exact hook definition". Whether it reads the hooks in `.claude/settings.json`: not documented as of 2026-11-25; searched [Hooks](https://developers.openai.com/codex/hooks.md).
- Gemini CLI reads `GEMINI.md` by default; it reads `AGENTS.md` only when the `context.fileName` setting in its `settings.json` lists it, as in the page's example `"fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"]`. (read 2026-11-25, [source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/gemini-md.md))
- Gemini CLI, skills and hooks: workspace skills live in `.gemini/skills/` or `.agents/skills/`, user skills in `~/.gemini/skills/` or `~/.agents/skills/`; `.claude/skills` is not named. Its hooks are its own, in `.gemini/settings.json`, with other event names (`BeforeTool`, `AfterAgent` and others), so Claude Code's hook entries do not carry over. (read 2026-11-25, [source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/skills.md), [source](https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/hooks/index.md))
- Cursor: "Cursor supports AGENTS.md in the project root and subdirectories." Its own rules are `.mdc` files in `.cursor/rules`; its CLI "also reads `AGENTS.md` and `CLAUDE.md` at the project root". (read 2026-11-25, [source](https://cursor.com/docs/rules.md), [source](https://cursor.com/docs/cli/using.md))
- Cursor's older `.cursorrules` file: not documented as of 2026-11-25; searched [Rules](https://cursor.com/docs/rules.md) and [Using the CLI](https://cursor.com/docs/cli/using.md).
- Cursor, skills: it loads `.agents/skills/` and `.cursor/skills/`, and "For compatibility, Cursor also loads skills from Claude and Codex directories: `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/`, and `~/.codex/skills/`." (read 2026-11-25, [source](https://cursor.com/docs/skills.md))
- Cursor, hooks: its own are in `.cursor/hooks.json`, and "Claude Code hooks load when **Include Third-Party Plugins, Skills, and Other Configs** is enabled in Cursor Settings → Agents → Third-Party Imports. The setting is on by default." They come from `.claude/settings.local.json`, `.claude/settings.json` and `~/.claude/settings.json`. The setting's name covers the imported plugins, skills and other configs too, so turning it off also stops the skills it loads from `.claude/skills/`. (read 2026-11-25, [source](https://cursor.com/docs/reference/third-party-hooks.md))
- GitHub Copilot: repository instructions are `.github/copilot-instructions.md`, and path-specific ones `.instructions.md` files under `.github/instructions`. Its agent reads `AGENTS.md` files anywhere in the repository, the nearest one first, or a single `CLAUDE.md` or `GEMINI.md` at the root; which surface reads which file is in its support table. (read 2026-11-25, [source](https://raw.githubusercontent.com/github/docs/main/content/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions.md), [source](https://raw.githubusercontent.com/github/docs/main/content/copilot/reference/custom-instructions-support.md))
- GitHub Copilot, skills: project skills in `.github/skills`, `.claude/skills` or `.agents/skills`. (read 2026-11-25, [source](https://raw.githubusercontent.com/github/docs/main/content/copilot/concepts/customizations/agent-skills.md))
- GitHub Copilot, hooks: its cloud agent loads `.github/hooks/*.json` only. Its CLI also loads user and inline hooks, and among its sources "Cross-tool `.claude/settings.json` and `.claude/settings.local.json` files in the repository are also read." VS Code's Copilot harness "also reads repository `.claude/settings.json` and `.claude/settings.local.json`". Neither page names `~/.claude/settings.json`. VS Code's hooks page adds: "Sharing a hook file location does not establish runtime compatibility." (read 2026-11-25, [source](https://raw.githubusercontent.com/github/docs/main/content/copilot/reference/hooks-reference.md), [source](https://raw.githubusercontent.com/microsoft/vscode-docs/main/docs/agent-customization/hooks.md))
- GitHub Copilot, turning hooks off: there is no switch for the Claude Code files alone. In VS Code, `chat.useHooks` set to `false` in User settings turns off repository and custom-agent hooks; in the CLI, "Set `disableAllHooks` to `true` at the top level to skip every hook in the file without deleting it." (read 2026-11-26, [source](https://raw.githubusercontent.com/microsoft/vscode-docs/main/docs/agent-customization/hooks.md), [source](https://raw.githubusercontent.com/github/docs/main/content/copilot/reference/hooks-reference.md))
- Windsurf's agent pages now redirect to Devin Local, which "shares its agent harness with Devin CLI". "`AGENTS.md`, `AGENTS.local.md` (for personal rules you keep out of version control), and `AGENT.md` are all read as always-on rules"; so is `CLAUDE.md`. Its own rules are in `.devin/rules/` and `.devin/global_rules.md`, and "The legacy `.windsurf/rules/*.md`, `.windsurf/global_rules.md`, and `.windsurfrules` files are imported by default." It also reads Cursor's `.cursor/rules/`. Skills come from `.devin/skills/`, `.agents/skills/` and `.windsurf/skills/`, and from `.claude/skills/` through its Claude Code import. (read 2026-11-25, [source](https://docs.devin.ai/desktop/devin-local/customizations), [source](https://docs.devin.ai/cli/extensibility/rules.md), [source](https://docs.devin.ai/cli/reference/configuration/read-config-from.md))
- Devin, hooks: its own are in `.devin/hooks.v1.json`, and "Existing hooks in `.claude/` directories are also picked up automatically", from `.claude/settings.json`, `.claude/settings.local.json` and the user-level Claude files. "Hooks from `.claude/` paths are loaded when `read_config_from.claude` is enabled (the default)." That one switch also governs the rest of the import: its `claude` option will "Import rules, skills, and MCP servers from Claude Code", so turning it off drops those too. (read 2026-11-25, [source](https://docs.devin.ai/cli/extensibility/hooks/overview.md), [source](https://docs.devin.ai/cli/reference/configuration/read-config-from.md))
- opencode reads `AGENTS.md`, and `CLAUDE.md` in a folder without one; it reads skills from `.opencode/skills/`, and also from `.claude/skills` and `.agents/skills`. Kiro reads `AGENTS.md` beside its own `.kiro/steering/` files, and skills from `.kiro/skills/`. Their hooks are their own: opencode's plugins "add tools, hooks, integrations, commands, agents, and other behavior", and Kiro's hooks are JSON files in `.kiro/hooks/`, each with a trigger, an optional matcher and an action. Neither page names Claude Code's `settings.json`. (read 2026-11-25, [source](https://opencode.ai/docs/rules/), [source](https://opencode.ai/docs/skills/), [source](https://opencode.ai/docs/plugins/), [source](https://kiro.dev/docs/steering/), [source](https://kiro.dev/docs/skills/), [source](https://kiro.dev/docs/hooks/))
