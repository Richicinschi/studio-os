# Scan triage

The triage of every gated item that SkillSpector rated other than `SAFE`, or rated `SAFE` with findings, kept beside `scans.json`: one section per item, one row per finding. A finding is a false positive (FP) when the matched text cannot do what the rule fears; "by design" (BY DESIGN) means it does what the item is for, which you weigh when you adopt it.

Each item's record in `scans.json` carries the hash of the content the scan read (`itemHash`): when any file of the item changes, `scan.mjs --check` and a release's triage gate say so, even where every finding stays on the same line, so a row that rests on text away from its line (an AE1 row's target file, a file read only in part) is read again.
- **Stable:** the same command ran twice, and a third time keeping the raw reports; every item's verdict, score and findings matched in all three. Its report also says which files it read only in part (`analysis_completeness`). A file read in part that another file links to becomes an AE1 finding; an item where nothing was found but one of its own files was read in part is rated `CAUTION` at 0/100 (`git-cleanup`, `finishing-a-development-branch`). The reasons met here are its bounded parser stopping at quoting it could not resolve (an apostrophe in prose, a `<test command>` placeholder in a shell block, code examples), its check for hidden instructions stopping at a removal word followed by quoted text (most often the item's own example of injection text, such as "ignore your instructions", inside its rule to treat files as data), and a size limit.
