# Facts the kit depends on

These change. Every fact here has its source and the date it was checked; the export reports this page when it is older than 90 days. Pages that rely on a fact link here instead of restating it.

## Models: which for what

- The current models are Claude Fable 5.1 (`claude-fable-5-1`), Opus 5.5 (`claude-opus-5-5`), Sonnet 5.5 (`claude-sonnet-5-5`) and Haiku 5.5 (`claude-haiku-5-5`). ([source](https://platform.claude.com/docs/en/models/overview))
- Anthropic's starting advice: "If you're unsure which model to use, start with Claude Opus 5.5 for most workloads. Use Claude Fable 5.1 for demanding reasoning and long-horizon agentic work." ([source](https://platform.claude.com/docs/en/models/overview))
- By kind of task: Fable 5.1 for multi-hour agent sessions and deep research; Opus 5.5 for long autonomous coding, large refactors and computer use; Sonnet 5.5 for everyday coding, data analysis and content; Haiku 5.5 for real-time, high-volume, cost-sensitive work and subagent tasks. ([source](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model))
- In Claude Code the model aliases are `opus` (complex reasoning), `sonnet` (daily coding), `haiku` (simple tasks) and `fable` (the hardest and longest-running tasks). ([source](https://code.claude.com/docs/en/model-config))
- Claude Code's default model on the Pro, Max, Ultra, Team and Enterprise plans and on the API is Opus 5.5; Fable is the default on none. ([source](https://code.claude.com/docs/en/model-config))
- Claude Code's effort levels: `medium` fits day-to-day work with a clear scope, `high` fixing a bug in an existing codebase, and `max` finding security vulnerabilities, though it is "prone to overthinking". ([source](https://code.claude.com/docs/en/model-config))
- The claude.ai model menu lists Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable 5.1, Opus 5, Sonnet 5, Opus 4.7, Opus 4.6 and Sonnet 4.6. Which plan gets which model, and the claude.ai default: not documented as of 2026-11-02. ([source](https://support.claude.com/en/articles/8664678-how-can-i-change-the-model-version-that-i-m-chatting-with))
- The context window of each current model (Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5) is 1M tokens, "roughly 555k words or 2.5M Unicode characters". In Claude Code these models "run with the 1M window by default"; `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` keeps sessions at 200K. ([source](https://platform.claude.com/docs/en/models/overview), [source](https://code.claude.com/docs/en/model-config))

## Prompt cache and why a new day starts cold

- In Claude Code the main conversation's cache lives one hour on a Claude subscription within plan usage, and five minutes on usage credits, an API key or a cloud provider; subagents' caches live five minutes. ([source](https://code.claude.com/docs/en/prompt-caching))
- Each cache hit resets the timer; "after a long enough gap, the next request recomputes the full input and re-establishes the cache." ([source](https://code.claude.com/docs/en/prompt-caching))
- So a conversation resumed the next day is past every cache lifetime, and its first request reprocesses the whole history with no cache hits. How that counts against a subscription's usage: not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/prompt-caching))
- Compacting after a long break "reprocesses that history as uncached input. This is why /compact costs the most when you resume an old session." ([source](https://code.claude.com/docs/en/prompt-caching))
- Switching model with `/model` makes the next request read the entire conversation with no cache hits. ([source](https://code.claude.com/docs/en/prompt-caching))
- To see which cache lifetime applies to you: `claude -p "hello" --output-format json`, then read `usage.cache_creation`. ([source](https://code.claude.com/docs/en/prompt-caching))
- On the API, a cache write costs 1.25 times the input price for five minutes and 2 times for one hour; a cache read costs 0.1 times (0.05 on Opus 5.5 and Sonnet 5.5, 0.025 on Fable 5.1); the default lifetime is five minutes. ([source](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))
- How claude.ai chats are cached: not documented as of 2026-11-02.

## Claude Code: context commands, subagents, extra folders

- `/clear` starts a new conversation with empty context and keeps project memory; its aliases are `/reset` and `/new`. ([source](https://code.claude.com/docs/en/commands))
- `/compact [instructions]` frees context by summarizing the conversation so far, optionally focused by the instructions you pass. ([source](https://code.claude.com/docs/en/commands))
- Claude Code compacts automatically as the conversation nears its context limit; `/autocompact` sets an earlier trigger, for example `/autocompact 500k`. ([source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/model-config))
- After a compaction the project-root `CLAUDE.md`, unscoped rules and auto memory are read again from disk, up to five recent files are re-read, and skill bodies are capped at 5,000 tokens each and 25,000 in all. Instructions given only in the conversation can be lost. ([source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/memory))
- A subagent works in its own context window; only its summary and a small metadata trailer come back to the main conversation. ([source](https://code.claude.com/docs/en/context-window))
- `--add-dir` gives Claude read and edit access to more folders, for example `claude --add-dir ../apps ../lib`; the reference adds that Claude Code does not discover most `.claude/` configuration from them. ([source](https://code.claude.com/docs/en/cli-reference))
- The pages differ on what an added folder brings: the skills page says skills in its `.claude/skills/` load, and the memory page says its `CLAUDE.md` loads only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. ([source](https://code.claude.com/docs/en/skills), [source](https://code.claude.com/docs/en/memory))

## Claude Code: where skills, agents and instruction files load from

- Project skills are `.claude/skills/<name>/SKILL.md`, found in the folder Claude Code starts in and in every parent folder up to the repository root; skills in nested subfolders load when Claude works in that subfolder. ([source](https://code.claude.com/docs/en/skills))
- User skills are `~/.claude/skills/<name>/SKILL.md`, for every project on the machine. When two have the same name, enterprise wins over personal, and personal over project. ([source](https://code.claude.com/docs/en/skills))
- Subagents are Markdown files with YAML front matter (`name` and `description` required; the body is the subagent's instructions): `.claude/agents/<name>.md` for a project, `~/.claude/agents/<name>.md` for every project. ([source](https://code.claude.com/docs/en/sub-agents))
- A subagent's `tools` field is an allowlist of the tools it may use, written as `Read, Grep, Bash` or as a YAML list. Left out, the subagent "inherits every tool available to subagents". `disallowedTools` is a denylist, applied first. Some tools never reach a subagent even when listed, `AskUserQuestion` among them. `Bash` "executes shell commands in your environment", so a subagent given `Bash` can change files without `Write` or `Edit`; a `Bash(git push *)` entry in `disallowedTools` "still removes the whole tool". ([source](https://code.claude.com/docs/en/sub-agents), [source](https://code.claude.com/docs/en/tools-reference))
- A subagent's `model` field takes `sonnet`, `opus`, `haiku`, `fable`, a full model ID, or `inherit` ("use the same model as the main conversation"). Left out, the model is, in order: the one Claude passes for that call, if any; `CLAUDE_CODE_SUBAGENT_MODEL`, if you set it; otherwise the main conversation's model. ([source](https://code.claude.com/docs/en/sub-agents))
- Claude Code ignores a subagent front matter field it does not recognize, without an error. ([source](https://code.claude.com/docs/en/sub-agents))
- "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation." Claude resumes a subagent with the `SendMessage` tool, and "a subagent that has the `SendMessage` tool can send that message too". ([source](https://code.claude.com/docs/en/sub-agents))
- Whether the claude.ai chat app (as opposed to Claude Code) has subagents: not documented as of 2026-11-02; the subagent pages describe Claude Code only. ([source](https://code.claude.com/docs/en/sub-agents), [source](https://code.claude.com/docs/en/feature-availability))
- `disable-model-invocation: true` in a skill's front matter: "Claude can't invoke the skill on its own"; you still run it by typing `/<name>`. Its description is then not in context, and the full skill loads when you invoke it. ([source](https://code.claude.com/docs/en/skills))
- `CLAUDE.md` and `CLAUDE.local.md` load at launch from the working folder and every folder above it, root first; those in subfolders load when Claude works there. ([source](https://code.claude.com/docs/en/memory))
- `AGENTS.md` is read only when no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` exists in the working folder or above (Claude Code v2.1.277 and later); the setting value `claude-md-and-agents-md` loads both. The documented way to keep one shared file is a `CLAUDE.md` that contains the line `@AGENTS.md`. ([source](https://code.claude.com/docs/en/memory))
- Auto memory loads the first 200 lines or 25 KB of its `MEMORY.md` at the start of each session. ([source](https://code.claude.com/docs/en/memory))
- The user folder is `~/.claude` on macOS and Linux and `%USERPROFILE%\.claude` on Windows. ([source](https://code.claude.com/docs/en/claude-directory))
- `CLAUDE_CONFIG_DIR` moves that folder, with all settings, session history and plugins. ([source](https://code.claude.com/docs/en/env-vars))

## Claude Code: MCP servers

- A remote server is added with `claude mcp add --transport http <name> <url>`, for example `claude mcp add --transport http notion https://mcp.notion.com/mcp`; a token goes in a header, `--header "Authorization: Bearer your-token"` (short forms `-t`, `-H`). ([source](https://code.claude.com/docs/en/mcp))
- A local server is added with `claude mcp add [options] <name> -- <command> [args...]`, for example `claude mcp add --env AIRTABLE_API_KEY=YOUR_KEY --transport stdio airtable -- npx -y airtable-mcp-server`; everything after `--` goes to the server unchanged. ([source](https://code.claude.com/docs/en/mcp))
- `claude mcp list` shows each server's state (connected, needs authentication, failed), `claude mcp get <name>` one server, and `/mcp` the same inside a session. `claude mcp remove <name>` removes a server; for a remote one, `claude mcp logout <name>` first revokes its stored sign-in, which removing alone does not. ([source](https://code.claude.com/docs/en/mcp))
- Scopes: **local** (the default) loads in the current project and is private to you; **project** loads in the current project and is shared through version control; **user** loads in all your projects. Local and user servers are stored in `~/.claude.json`, project servers in `.mcp.json` at the project root (`--scope project`). When two share a name, local wins over project, project over user, user over plugins, plugins over claude.ai connectors. ([source](https://code.claude.com/docs/en/mcp))
- The docs say to check `.mcp.json` into version control so a team gets the same servers, and to keep machine-specific paths and secrets out of it by referring to variables: `${VAR}` and `${VAR:-default}` expand in a server's command, arguments, environment, URL and headers, for example `"Authorization": "Bearer ${API_KEY}"`. ([source](https://code.claude.com/docs/en/mcp))
- Secrets reach a local server through `--env` / `-e KEY=value`, and a remote one through `--header`. ([source](https://code.claude.com/docs/en/mcp))
- Trust: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." An interactive session asks before it uses a project's servers (`claude mcp reset-project-choices` resets the answers); `claude -p` loads them without asking. ([source](https://code.claude.com/docs/en/mcp))
- On Team and Enterprise plans, the MCP page says only admins can add servers; the claude.ai connector pages say an Owner adds a connector for the organization. ([source](https://code.claude.com/docs/en/mcp), [source](https://claude.com/docs/connectors/getting-started))
- Signing in to a remote server: run `/mcp` in a session, "Then follow the steps in your browser to log in"; if the browser does not open, copy the URL Claude Code shows. From a terminal, `claude mcp login <name>`. A `claude -p` run cannot sign in, so sign in from an interactive session first. Tokens "are stored securely and refreshed automatically", and "Clear authentication" in the `/mcp` menu revokes access. ([source](https://code.claude.com/docs/en/mcp))
- Where a value typed after `--env` or `--header` ends up: not stated outright on the MCP page as of 2026-11-02. Local and user servers are stored in `~/.claude.json` (above), and the page says Claude Code checks "the values and key names under `env` and `headers`" of a server's configuration and "uses the values exactly as written". The kit therefore treats such a value, or one the shell fills in from `"$NAME"`, as written into `~/.claude.json` in plain text. ([source](https://code.claude.com/docs/en/mcp), [source](https://code.claude.com/docs/en/settings))
- A `${VAR}` reference also works for local and user servers, not only in `.mcp.json`: the page names "a local- or user-scoped server entry in `~/.claude.json`", and for "a server in the local, project, or user scope", `/mcp`, `claude mcp list` and `claude mcp get` "show a `${VAR}` reference by name rather than as its resolved value". None of the page's `claude mcp add` examples passes a reference; `claude mcp add-json <name> '<json>'` takes a server entry as JSON in single quotes, and `--scope user` puts it in your user configuration. In a remote server's `url` and `headers`, credential variables of Claude Code and your environment, such as `ANTHROPIC_API_KEY`, `HTTPS_PROXY` and `NPM_TOKEN`, "read as empty" instead of expanding. ([source](https://code.claude.com/docs/en/mcp))

## Claude Code: the ! prefix, /init and local files

- Typing `!` before a command runs it as a shell command directly, without Claude, for example `! npm test` or `! git status`; its output goes into the conversation and Claude responds to it. Where it runs (the working folder) is not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/interactive-mode#shell-mode-with-prefix))
- `!` commands run outside Claude Code's sandbox even when sandboxing is on, unless the session is in strict sandbox mode. ([source](https://code.claude.com/docs/en/interactive-mode#shell-mode-with-prefix))
- Whether a `!` command can take typed input while it runs, such as a password prompt, a passphrase or a sign-in that waits in the terminal: not documented as of 2026-11-02. The page lists what shell mode does (it adds the command and its output to the conversation, shows progress, and can go to the background with `Ctrl+B`) and says nothing about input. So the kit sends any step that asks for a password, a passphrase or a terminal sign-in to a separate terminal. ([source](https://code.claude.com/docs/en/interactive-mode#shell-mode-with-prefix))
- Whether a `!` command goes through `PreToolUse` hooks, the ones that check Claude's tool calls: not documented as of 2026-11-10. Shell mode runs a command "directly without going through Claude", and the hooks reference does not say whether its tool events cover shell mode. So a step that a hook refuses when Claude runs it, such as setting `core.hooksPath` under `git-guardrails`, goes to a separate terminal. ([source](https://code.claude.com/docs/en/interactive-mode#shell-mode-with-prefix), [source](https://code.claude.com/docs/en/hooks))
- `/init` writes a `CLAUDE.md` guide at the project root from an analysis of the code; when one exists it suggests improvements rather than overwriting it. ([source](https://code.claude.com/docs/en/commands), [source](https://code.claude.com/docs/en/memory))
- `CLAUDE.local.md` at a project root holds private per-project instructions. It is supported, and git does not ignore it by itself: "Add `CLAUDE.local.md` to your `.gitignore` so it isn't committed." ([source](https://code.claude.com/docs/en/memory))
- A `CLAUDE.local.md` counts as a Claude file, so where one exists Claude Code no longer reads an `AGENTS.md` there by default; a `CLAUDE.local.md` that should keep it loaded imports it with the line `@AGENTS.md`. ([source](https://code.claude.com/docs/en/memory))
- `.claude/settings.local.json` holds your settings for one project. Claude Code keeps it out of git when it creates the file itself (through a global git excludes entry); a hand-made one must be added to `.gitignore`. ([source](https://code.claude.com/docs/en/settings))

## Claude Code: measuring context and asking multiple choice

- `/context` shows "a live breakdown by category with optimization suggestions, including which CLAUDE.md and auto memory files loaded". Its units: not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/commands))
- Whether `/context` output reaches Claude or only the person: not documented as of 2026-11-02. The commands page says it only of other commands (`/release-notes` appear "without entering the conversation Claude sees"). So the kit's audit estimates instead, from file sizes (bytes divided by 4), labels the number an estimate, and you can type `/context` yourself to see the live breakdown. ([source](https://code.claude.com/docs/en/commands))
- "Before you type anything: CLAUDE.md, auto memory, MCP tool names, and skill descriptions all load into context." A skill's full content loads only when it is used. ([source](https://code.claude.com/docs/en/context-window), [source](https://code.claude.com/docs/en/skills))
- Subagent descriptions "take up context, so keep them short"; a subagent's own instructions load only when it runs. Exactly when the descriptions load: not documented as of 2026-11-02; the kit counts them as every session. ([source](https://code.claude.com/docs/en/sub-agents))
- The list of skill descriptions has a budget of 1% of the context window, 8,000 characters when that cannot be worked out; `SLASH_COMMAND_TOOL_CHAR_BUDGET` overrides it. Past the budget every skill name stays, and the descriptions of the skills you use least are dropped first. One skill's description is capped at 1,536 characters. ([source](https://code.claude.com/docs/en/skills), [source](https://code.claude.com/docs/en/env-vars))
- Files a `CLAUDE.md` imports with `@` load at launch with it, up to four imports deep; a file over 4 MiB is skipped. ([source](https://code.claude.com/docs/en/memory))
- The multiple-choice tool is `AskUserQuestion`: it "asks multiple-choice questions to gather requirements or clarify ambiguity". Questions per call, choices per question and multi-select: not documented as of 2026-11-02. Observed in the tool's own definition in Claude Code on 2026-11-02, not in the docs: one to four questions a call, two to four choices each, multi-select available. ([source](https://code.claude.com/docs/en/tools-reference))
- `/agents` prints a reminder to ask Claude to create or manage subagents, or to edit `.claude/agents/` or `~/.claude/agents/` directly; `/hooks` shows the hook configuration; `/mcp` sets up and lists MCP servers, and in print mode prints a text summary of their status. A `/skills` command: not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/commands))
- Variables under the `env` key of a `settings.json` file apply to every session and its subprocesses, however `claude` was started: `~/.claude/settings.json` for you in every project, `.claude/settings.json` shared with a project, `.claude/settings.local.json` for you in one project. ([source](https://code.claude.com/docs/en/env-vars), [source](https://code.claude.com/docs/en/settings))
- With `--permission-prompts none`, Claude Code removes the tools that need an answer from a person, `AskUserQuestion` among them. In a plain `claude -p` run: not documented as of 2026-11-02. The kit's drill asks with a numbered checklist whenever the tool is not offered. ([source](https://code.claude.com/docs/en/headless))

## Claude Code: hooks

- A hook is configured under the `hooks` key of a settings file, by event, then a matcher group, then a list of handlers, for example `"PreToolUse": [ { "matcher": "Bash", "hooks": [ { "type": "command", "command": "..." } ] } ]`. The files: `~/.claude/settings.json` (all your projects), `.claude/settings.json` (one project, can be committed), `.claude/settings.local.json` (one project, kept out of git when Claude Code writes it). ([source](https://code.claude.com/docs/en/hooks-guide))
- `Stop` runs "when the main Claude Code agent has finished responding", not after an interrupt by the user. A Stop hook that exits 2 "prevents Claude from stopping, continues the conversation", and Claude receives its stderr as the reason. Its input carries `stop_hook_active`, "`true` when Claude Code is already continuing as a result of a stop hook", so a hook can let the second stop through. ([source](https://code.claude.com/docs/en/hooks#stop))
- `SessionStart` runs "when a session begins or resumes", with the matchers `startup`, `resume`, `clear`, `compact` and `fork`. Claude Code "adds plain-text stdout as context that Claude can see and act on"; exit 2 there only shows stderr to the person. ([source](https://code.claude.com/docs/en/hooks-guide), [source](https://code.claude.com/docs/en/hooks))
- A `PreToolUse` hook that exits 2 blocks the tool call, and its stderr is the message Claude gets. A matcher of letters, digits and `|` is a list of exact tool names, so `Bash|PowerShell` covers both tools. ([source](https://code.claude.com/docs/en/hooks))
- Command hooks run through `sh -c` on macOS and Linux, and on Windows through Git Bash, or PowerShell when Git Bash is not installed. How a path inside `node "<path>"` is treated on Windows: not documented as of 2026-11-02. ([source](https://code.claude.com/docs/en/hooks))
- `/hooks` opens a read-only list of the configured hooks, each labelled with where it comes from. ([source](https://code.claude.com/docs/en/hooks-guide))

## Claude Code: permission rules for secret files

Checked on 2026-11-09, and run once on Windows with Claude Code 2.1.319 in a throwaway folder: `claude -p` reading only that folder's settings (`--setting-sources project`), with the deny rules of [the sensitive-file deny rules card](../cards/sensitive-file-deny-rules.md) and a made-up value in each file.

- A permission rule is `Tool` or `Tool(specifier)`, listed under `permissions.allow`, `permissions.ask` or `permissions.deny` in a settings file. "Permission rules are enforced by Claude Code, not by the model": instructions in a prompt or a `CLAUDE.md` "shape what Claude tries to do, but they don't change what Claude Code allows." ([source](https://code.claude.com/docs/en/permissions#manage-permissions))
- Rules are checked in the order deny, ask, allow, and the first match decides; "An allow rule can't carve an exception out of a deny rule." A tool denied at any level cannot be allowed by another, and a list such as `permissions.deny` set in several files is combined, not replaced. ([source](https://code.claude.com/docs/en/permissions#settings-precedence), [source](https://code.claude.com/docs/en/settings#lists-merge-instead-of-overriding))
- The files: `~/.claude/settings.json`, for you in every project (`%USERPROFILE%\.claude` on Windows; `CLAUDE_CONFIG_DIR` moves the folder); `.claude/settings.json`, shared with everyone in a project once committed; `.claude/settings.local.json`, for you in one project; and managed settings from an organization. Settings files are strict JSON: "a `//` comment or a trailing comma is a syntax error". ([source](https://code.claude.com/docs/en/settings))
- `deny` and `ask` rules in a project's `.claude/settings.json` apply at once; its `allow` rules wait until you accept the workspace trust dialog. ([source](https://code.claude.com/docs/en/permissions#project-allow-rules-and-workspace-trust))
- An organization's managed settings can set `allowManagedPermissionRulesOnly`, which "makes managed settings the only settings source of permission rules". ([source](https://code.claude.com/docs/en/permissions#managed-settings))
- The settings page's own example stops Claude Code reading `.env` files from `~/.claude/settings.json` with `"deny": ["Read(./.env)", "Read(./.env.*)"]`. ([source](https://code.claude.com/docs/en/settings#edit-a-settings-file))
- `Read` and `Edit` rules use gitignore pattern syntax. `//path` is an absolute path from the filesystem root; `~/path` starts at your home folder; `/path` starts at the settings source, which for `~/.claude/settings.json` is `~/.claude`, not the project; `path` or `./path` starts at the current folder. A bare file name matches at any depth below the current folder, and `Read(//**/.env)` blocks "any `.env` anywhere on the filesystem". On Windows a path is turned into POSIX form before matching (a path on `C:\` starts `/c/`), and `//**/.env` matches on every drive. ([source](https://code.claude.com/docs/en/permissions#how-path-patterns-match))
- A rule that starts with `!` carves paths out of the rules listed before it in the same file, but only out of `path` or `./path` rules: it "can't reach a rule anchored with" `/`, `~/` or `//`. ([source](https://code.claude.com/docs/en/permissions#read-and-edit))
- What a `Read` deny rule covers: the Read tool; "a best-effort attempt" for the other built-in tools that read files, such as Grep and Glob; `@file` mentions and the context a connected IDE shares; pasted image paths and directory listings, from v2.1.290. It also blocks Edit and Write on the same path, creating a new file there included (Write from v2.1.228), but not NotebookEdit. The settings reference sums it up: Claude Code "excludes matching files from file discovery and search results, denies reads of them, and blocks the Edit and Write tools on the matching paths." ([source](https://code.claude.com/docs/en/permissions#read-and-edit), [source](https://code.claude.com/docs/en/settings-reference#permissions-deny))
- In the shell, `Read` and `Edit` deny rules "apply to Claude's built-in file tools, to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, `sed`, and `tee`, and to the targets of Bash redirections" (input redirects such as `< file` from v2.1.257). "They don't apply to a command that reads files without naming them, such as `grep -r pattern .` run from the directory that holds the file, or to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself." ([source](https://code.claude.com/docs/en/permissions#read-and-edit), [source](https://code.claude.com/docs/en/settings-reference#permissions-deny))
- `cat`, `head`, `grep` and `find` are among the read-only commands that run without a permission prompt in every mode. On macOS, Linux and WSL, Claude Code leaves the Glob and Grep tools out by default, and Claude searches with `find` and `grep` through Bash; "In Claude's shell those two commands run embedded versions of `bfs` and `ugrep`". ([source](https://code.claude.com/docs/en/permissions#read-only-commands), [source](https://code.claude.com/docs/en/tools-reference#glob-tool-behavior))
- Whether `Read` deny rules apply to PowerShell commands: not documented as of 2026-11-09; the PowerShell section covers command rules only. ([source](https://code.claude.com/docs/en/permissions#powershell))
- MCP tools are matched by name: `mcp__<server>__<tool>` for one tool, `mcp__<server>__*` for all of a server's. The `Read` rules' list of what they cover names built-in tools and no MCP tool, and "When Claude Code loads a settings file, it skips any `mcp__` rule that has parentheses", so a settings file can deny an MCP tool only as a whole, not for one path. ([source](https://code.claude.com/docs/en/permissions#mcp), [source](https://code.claude.com/docs/en/permissions#match-by-input-parameter), [source](https://code.claude.com/docs/en/permissions#read-and-edit))
- A mod (code a plugin runs inside Claude Code) that approves tool calls "can approve a call that a deny rule refuses" in a session with neither managed settings nor a Team or Enterprise `/login`. ([source](https://code.claude.com/docs/en/permissions#extend-permissions-with-hooks))
- For a limit that holds for every program a shell command starts, the docs point to the sandbox. It "runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed." It covers shell commands only, and `Read` and `Edit` deny rules are merged into its configuration. ([source](https://code.claude.com/docs/en/sandboxing), [source](https://code.claude.com/docs/en/sandboxing#permission-rules))
- `/permissions` lists every rule and the settings file it comes from, and you can add or remove a rule there; "A rule you add through `/permissions` follows the row for the settings file you save it to", so it is saved to the file you pick. The dialog's steps are not documented as of 2026-11-09. A malformed rule raises a Settings Warning and is skipped while the rest of the file stays in effect, and `claude doctor` lists the entries Claude Code rejected. Claude Code reloads a settings file when it changes, permission edits included, without a restart. ([source](https://code.claude.com/docs/en/permissions#manage-permissions), [source](https://code.claude.com/docs/en/permissions#how-path-patterns-match), [source](https://code.claude.com/docs/en/settings#fix-a-broken-settings-file), [source](https://code.claude.com/docs/en/settings#when-edits-take-effect))
- A `.claudeignore` file has no effect; `permissions.deny` replaces the deprecated `ignorePatterns`. ([source](https://code.claude.com/docs/en/permissions#read-and-edit), [source](https://code.claude.com/docs/en/settings-reference#permissions-deny))
- Observed in the Windows run, not stated in the docs: the Read tool refused `.env`, a `.env.` file with a suffix after the dot, `.envrc`, `client_secret.json`, `server.pem` and `sub/Credentials.json` (a capital C, under the rule `*credential*`) with `File is in a directory that is denied by your permission settings.`, and read an ordinary file. Bash `cat .env`, `cat < .env`, `grep CANARY .env` and `head -1 client_secret.json` were refused with `Permission to use Bash with command <command> has been denied.` `grep -r CANARY .` and `grep -r <value> <folder>` printed the lines of the denied files. A Node one-liner reading `.env`, allowed for the run, printed it. PowerShell `Get-Content .env` was refused, with a message about the session's working folders, while `Get-Content` of an ordinary file worked; `Get-ChildItem -Recurse -File | Select-String -Pattern CANARY`, allowed for the run, printed every denied file's line. The Grep tool's search and a Glob of `**/*` left the denied files out; `ls -a` listed their names.
- Observed in a review run, Claude Code 2.1.319 on Windows, not stated in the docs: the same rules refused files inside folders whose names match, as gitignore patterns do: `my-secrets/notes.txt`, `aws-credentials-helper/src/app.js`, `keys.key/readme.txt`, and every file of a project kept in a folder named `secret-garden`. So a rule matches a file or a folder anywhere in the path, the project folder and the folders above it included.

## Claude Code: the sandbox

Checked on 2026-11-09. The kit does not set the sandbox up; these facts say what it would add. ([source](https://code.claude.com/docs/en/sandboxing))

- The sandbox is "a boundary that the operating system enforces around the shell commands Claude runs on your machine": its limits apply to Bash, PowerShell and Monitor commands "and the processes they start". It "covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it", and a `denyRead` entry "doesn't stop the Read tool". ([source](https://code.claude.com/docs/en/sandboxing))
- "The sandbox runs on macOS, Linux, and WSL2. On native Windows, Claude Code runs commands unsandboxed." It is off by default; `/sandbox` in a session or `sandbox.enabled: true` in a settings file turns it on. ([source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts))
- Network: a sandboxed command has "No direct route out. Connections go through a proxy on your machine that checks each host against your allowed domains, which start empty", set with `sandbox.network.allowedDomains`; your permission mode decides what happens to other hosts, and `sandbox.network.strictAllowlist`, set in user, managed or `--settings` settings, refuses them without asking. `allowedDomains` "doesn't limit WebFetch", which follows permission rules instead. ([source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts), [source](https://code.claude.com/docs/en/sandboxing#hosts-outside-your-allowed-domains))
- Files: by default a sandboxed command can read "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`"; `sandbox.filesystem.denyRead` narrows that. ([source](https://code.claude.com/docs/en/sandboxing#what-the-sandbox-restricts))
- What still runs outside it: a command you type after `!` in most sessions, commands listed in `excludedCommands`, and a command Claude asks to run unsandboxed after it fails in the sandbox. ([source](https://code.claude.com/docs/en/sandboxing#what-runs-outside-the-sandbox))

## GitHub: merge methods

- A repository's `allow_merge_commit`, `allow_squash_merge` and `allow_rebase_merge` are read with `GET /repos/{owner}/{repo}` and changed with `PATCH /repos/{owner}/{repo}`, each "true to allow ... or false to prevent" that method. The permission needed to change them: not documented on that page as of 2026-11-02. ([source](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28#update-a-repository))
- With the `gh` command line: `gh api repos/{owner}/{repo} --jq '.allow_merge_commit, .allow_squash_merge, .allow_rebase_merge'` reads them, and `gh api -X PATCH repos/{owner}/{repo} -F allow_squash_merge=false -F allow_rebase_merge=false` changes them; `-F` sends `true` and `false` as real booleans, where `-f` would send text. gh replaces the placeholders `{owner}` and `{repo}`; where it takes their values from was not in the text checked on 2026-11-02, so name the repository when in doubt (`repos/<owner>/<repo>`). ([source](https://cli.github.com/manual/gh_api))
- On the web: the repository's Settings, "General", the "Pull Requests" section. ([source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests))
- `gh pr merge` takes `--merge` ("merge the commits with the base branch"), `--squash` or `--rebase`. What it does when the chosen method is switched off on the repository: not documented as of 2026-11-02. ([source](https://cli.github.com/manual/gh_pr_merge))
- A rebase merge on GitHub "Always updates the committer information and creates new commit SHAs", and with **Rebase and merge** "the commits in the head branch are added to the base branch without commit signature verification": GitHub creates a modified commit and "can't sign the commit on the user's behalf". The documented workaround is to rebase and merge locally, then push. ([source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github), [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification))
- `gh` "is supported for users on GitHub.com, GitHub Enterprise Cloud, and supported GitHub Enterprise Server versions"; its README names no other host. GitLab's own command line is `glab`, "an open source GitLab CLI tool". ([source](https://github.com/cli/cli), [source](https://docs.gitlab.com/cli/))

## Git: signed commits and identity per folder

Checked on 2026-11-02, and run once on Windows with git 2.54.0 in a throwaway folder (a temporary key and `GIT_CONFIG_GLOBAL` pointing at a temporary file).

- SSH signing came with git 2.34: "In addition to GnuPG, ssh public crypto can be used for object and push-cert signing." `gpg.format` takes `openpgp` (the default), `x509` or `ssh`. ([source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc), [source](https://git-scm.com/docs/git-config))
- GitHub shows a commit as Verified when its signature checks out "against a public key you have added to your account"; "SSH signature verification is available in Git 2.34 or later." ([source](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification))
- An SSH key goes on GitHub as one of two types, "either authentication or signing". To sign with the key you already push with, upload it again as a signing key: `gh ssh-key add <key>.pub --type signing`. GPG keys: `gh gpg-key add`. Both have `delete`; on the web, Settings, then "SSH and GPG keys". ([source](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account), [source](https://cli.github.com/manual/gh_ssh-key_add), [source](https://cli.github.com/manual/gh_gpg-key))
- Making a key, as GitHub's pages give it: `ssh-keygen -t ed25519 -C "your_email@example.com"`, which asks for a passphrase twice; `gpg --full-generate-key` (GnuPG 2.1.17 or later); and `gpg --armor --export <key ID>` prints a GPG public key to paste into GitHub. ([source](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent), [source](https://docs.github.com/en/authentication/managing-commit-signature-verification/generating-a-new-gpg-key))
- Telling git which key to use: for SSH, `git config --global gpg.format ssh` and `git config --global user.signingkey /PATH/TO/.SSH/KEY.PUB`; for GPG, `git config --global user.signingkey <key ID>`. `git config --global commit.gpgsign true` signs every commit. With `gpg.format` set to `ssh`, `user.signingKey` "can contain the path to either your private ssh key or the public key when ssh-agent is used"; `commit.gpgSign` is "A boolean to specify whether all commits should be GPG signed". ([source](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key), [source](https://git-scm.com/docs/git-config))
- An allowed-signers line holds "principals, options, keytype, base64-encoded key"; the option `namespaces="..."` "Specifies a pattern-list of namespaces that are accepted for this key", and the namespace in the signature must match. Git's SSH commit signatures carry the namespace `git` (the Windows run printed `Good "git" signature`), so `namespaces="git"` accepts the key for git signatures only. The file "can be set to a location outside of the repository and every developer maintains their own trust store." ([source](https://man.openbsd.org/ssh-keygen.1), [source](https://git-scm.com/docs/git-config))
- A GPG key is matched to "your committer identity and your verified email address". Whether an SSH signing key needs the commit email to match: not documented as of 2026-11-02. ([source](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key))
- Checking an SSH signature on your own machine needs `gpg.ssh.allowedSignersFile`: a file of lines, each the principals (an email address), then the public key. Without it git prints `error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification` and `No signature`. With it, `git log --show-signature -1` printed `Good "git" signature for <email> with ED25519 key SHA256:...` in the Windows run. ([source](https://git-scm.com/docs/git-config), [source](https://man.openbsd.org/ssh-keygen.1))
- For a GPG-signed commit, `git log --show-signature -1` printed `gpg: Good signature from "<name> <email>"` in the Windows run (GnuPG 2.4.9). ([source](https://git-scm.com/docs/git-log))
- A passphrase you type is kept by the GnuPG agent for `default-cache-ttl` seconds after its last use, and never longer than `max-cache-ttl`: 600 and 7,200 by default, as `gpgconf --list-options gpg-agent` printed on GnuPG 2.4.9. Both go in `gpg-agent.conf` in the GnuPG home folder. ([source](https://www.gnupg.org/documentation/manuals/gnupg/Agent-Options.html))
- On Windows, with `GNUPGHOME` set in Git Bash, git's signing call did not find the key in the probe: the folder reached GnuPG as a drive-letter path such as `X:/...`, which it read as relative. Passing `--homedir` through a small `gpg.program` script worked. Not documented as of 2026-11-02.
- One identity per folder: `includeIf "gitdir:<folder>/"` includes another config file for every repository under that folder; a pattern ending in `/` matches the folder and everything inside it, and `gitdir/i` matches without regard to case. The docs show forward slashes and say nothing of drive letters; in the Windows run, `gitdir:X:/work/`-style patterns (a drive letter, then forward slashes) worked, and `gitdir/i` matched the same drive letter in lower case. The run added each include from the command line, without opening the config file: `git config --global includeIf."gitdir:<folder>/".path <file>` (there with `--file` on a temporary config). ([source](https://git-scm.com/docs/git-config#_conditional_includes))
- `GIT_CONFIG_GLOBAL` (git 2.32) makes git read the given file instead of your global config; `GIT_CONFIG_NOSYSTEM` skips the system config; `GNUPGHOME` moves GnuPG's home folder, `~/.gnupg` by default. The kit's trial runs under all three so it never touches a real setup. ([source](https://github.com/git/git/blob/master/Documentation/RelNotes/2.32.0.adoc), [source](https://git-scm.com/docs/git-config#ENVIRONMENT), [source](https://www.gnupg.org/documentation/manuals/gnupg/Invoking-gpgconf.html))
- To undo a setting, `git config unset <key>` (newer git) or `git config --unset <key>`, which the docs now list as deprecated, in the same scope (`--global`, or inside the repository for a local one). ([source](https://git-scm.com/docs/git-config))
- Where GnuPG comes from: on Windows, Git for Windows carries a `gpg.exe` in its `usr\bin` folder (GnuPG 2.4.9 with git 2.54.0; not stated on its site), or Gpg4win installs it on its own; on macOS, `brew install gnupg`; on Debian and Ubuntu, `sudo apt install gnupg`. ([source](https://gpg4win.org/about.html), [source](https://formulae.brew.sh/formula/gnupg), [source](https://packages.debian.org/stable/gnupg))
- Windows 10 build 1809 and later offers OpenSSH, `ssh-keygen` included, as an optional feature; Git for Windows brings its own (OpenSSH 10.3 with git 2.54.0). ([source](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-overview))

## Git: hooks and worktrees

- "By default the hooks directory is `$GIT_DIR/hooks`" (`.git/hooks` in a normal repository). `core.hooksPath` moves it: "Git will try to find your hooks in that directory ... instead of in `$GIT_DIR/hooks`", so while it is set, hooks left in `.git/hooks` do not run. The path can be absolute or relative. ([source](https://git-scm.com/docs/githooks), [source](https://git-scm.com/docs/git-config))
- Setting `core.hooksPath` to `/dev/null` turns every hook off, the docs suggest for one command at a time: `git -c core.hooksPath=/dev/null ...`. ([source](https://git-scm.com/docs/git-config))
- A setting can also come from the environment: "If GIT_CONFIG_COUNT is set to a positive number, all environment pairs GIT_CONFIG_KEY_<n> and GIT_CONFIG_VALUE_<n> up to that number will be added to the process's runtime configuration." So `core.hooksPath` can be set for one command with no `-c` and no `git config`. ([source](https://git-scm.com/docs/git-config#ENVIRONMENT))
- Long options can be shortened: "Commands that support the enhanced option parser accepts unique prefix of a long option as if it is fully spelled out", for example "git commit --amen behaves as if you typed git commit --amend". Which prefix is unique depends on the command's other options. ([source](https://git-scm.com/docs/gitcli))
- `pre-commit` runs before the commit is made; "Exiting with a non-zero status from this script causes the `git commit` command to abort before creating a commit", and `git commit --no-verify` bypasses it. ([source](https://git-scm.com/docs/githooks))
- `git mv` moves or renames a file, a folder or a symlink and updates the index, "but the change must still be committed". `git log --follow <file>` will "Continue listing the history of a file beyond renames (works only for a single file)". ([source](https://git-scm.com/docs/git-mv), [source](https://git-scm.com/docs/git-log))
- `git worktree add -b <new-branch> <path> <commit-ish>` creates a worktree at `<path>` with a new branch "starting at `<commit-ish>`" (`HEAD` when left out); "By default, `-b` refuses to create a new branch if it already exists." ([source](https://git-scm.com/docs/git-worktree))
- `git worktree remove <worktree>`: "Only clean worktrees (no untracked files and no modification in tracked files) can be removed"; `--force` removes an unclean one, and "The main worktree cannot be removed." `git worktree prune` removes the records of worktrees whose folders are gone; `git worktree list` lists the main worktree first, then the linked ones. ([source](https://git-scm.com/docs/git-worktree))

## Installing SkillSpector

The same command on Windows, macOS and Linux, once uv is installed:

On Windows, turn on Python's UTF-8 mode before a scan, or the terminal report crashes with a `charmap` encoding error (seen on Windows 10 with the build that reports 2.2.3, on 2026-11-02):

```powershell
# PowerShell
$env:PYTHONUTF8=1
skillspector scan <path or git URL> --no-llm
```

```bash
# Git Bash on Windows (macOS and Linux terminals are UTF-8 already)
PYTHONUTF8=1 skillspector scan <path or git URL> --no-llm
```

- The README's install is `uv tool install git+https://github.com/NVIDIA/skillspector.git`; the package needs Python `>=3.12,<3.16`, which `--python 3.13` satisfies. ([source](https://github.com/NVIDIA/SkillSpector), [source](https://github.com/NVIDIA/SkillSpector/blob/main/pyproject.toml))

No 2.2.3 release exists: the oldest tag is v2.5.0 (2026-07-27), main's `pyproject.toml` says 2.12.0, and the newest tag is v2.13.3. ## Docker: a long job in a named container

- `docker run` options: `-d`, `--detach` ("Run container in background and print container ID"); `--name` ("Assign a name to the container"); `-m`, `--memory` ("Memory limit"); `--cpus` ("Number of CPUs"); `-v`, `--volume` ("Bind mount a volume"); `--rm` removes the container "and its associated anonymous volumes when it exits". ([source](https://docs.docker.com/reference/cli/docker/container/run/))
- A bind mount is read-only with `ro` after the path inside the container, for example `-v "$(pwd)"/target:/app:ro`. ([source](https://docs.docker.com/engine/storage/bind-mounts/))
- `--restart` defaults to `no`: "Don't automatically restart the container." `on-failure` restarts it after a non-zero exit, `always` whenever it stops, and `unless-stopped` the same except after you stop it. ([source](https://docs.docker.com/reference/cli/docker/container/run/), [source](https://docs.docker.com/engine/containers/start-containers-automatically/))
- `docker inspect` returns "low-level information on Docker objects", and `--format` prints it through a Go template, for example `docker inspect --format='{{.Config.Image}}' <container>`. `docker info` displays "system-wide information"; `docker info --format '{{json .}}'` prints it as JSON. ([source](https://docs.docker.com/reference/cli/docker/inspect/), [source](https://docs.docker.com/reference/cli/docker/system/info/))
- The field names `.State.ExitCode`, `.NCPU`, `.MemTotal` and `.ServerVersion` are not in the examples on these pages as of 2026-11-02, nor is what `docker info` prints when the engine is not running. `docker inspect <container>` and `docker info --format '{{json .}}'` print every field, so check a name there before relying on it. ([source](https://docs.docker.com/engine/cli/formatting/))
- `docker rm -v` (`--volumes`) removes the container's anonymous volumes with it; `-f` forces the removal of a running container. ([source](https://docs.docker.com/reference/cli/docker/container/rm/))
- Docker's install, its minimum version and its licence terms for use at a company: not checked for the kit as of 2026-11-02; follow Docker's own install guide.
