# Maintaining the kit

For whoever exports the kit from the studio. Adopters never need this page.

## What is generated and what isn't

`catalog/` and `docs/THIRD_PARTY_NOTICES.md` are generated from the studio's hub by the export. Never edit them by hand; edit `export.manifest.json`, the allowlist, instead. One catalog file comes from the kit's own cards: `catalog/DETECT.md`, the Detect section of every card in one file, which the drill's phase 1 reads instead of each card. The export writes it; after a card's Detect changes between exports, `node tools/export/detect.mjs` writes it again, and `npm test` fails until the committed file matches the cards. Each item and domain in `catalog/features.json` carries a `hash`: its shipped files, the files the manifest names for it, and its card, with the scan line left out. An adopter's `adoption/installed.json` keeps the hash of the version they took (`tools/installed.mjs`), so update mode can say which installed items the kit changed since; a catalog exported before this field has none, and the record says so. Everything else is hand-written: the entry pages, `modules/`, `templates/`, `examples/`, `docs/facts.md`, the two kit skills in `.claude/skills/`, and `tools/export/` itself.

**What the adoption reads.** The drill keeps its rules for every question in `SKILL.md` and each phase and mode in a file of its own (`phases/`, `modes/`), read when that phase or mode starts. `tools/export/phase-loads.mjs` adds up what each phase reads, and the export prints it as `load:` lines. START-HERE's table "What the adoption reads" states the same figures, with the median card and the menu below it, and `npm test` holds each within 10% and the load before the first question under 8,000 tokens. After a change to the drill, `ADOPT.md`, the menu, a card (its Detect is in phase 1's load, and the median card may move) or the templates a phase reads, update that table.

## Outside text and its credit

A domain ships only when `packShippable` passes: no file in it is an outside licence file, and no skill in it names an upstream, has an "adapted" author line or is a vendored copy not marked rewritten. It may still adapt outside text under a permissive licence, credited in a credit file: `ATTRIBUTION.md`, or a file whose name starts with `NOTICE`, at any depth. When the build finds one, the domain's `SOURCE.md` says it adapts outside work, names the licences of the adapted text and links the credit file, and `docs/THIRD_PARTY_NOTICES.md` lists the domain with a link to that file and to the text of each licence.

The build reads those licences from the credit file's tables: the column headed Licence, in every table except one whose header row or the heading above it says "not copied" or "never copied". A cell names one SPDX identifier or several (`MIT / Apache-2.0`). A credit file with no such table, a cell that is not an SPDX identifier, or only tables of sources not copied stops the export with the file and the row. Fix the credit file in the hub.

**Naming outside work.** A repo-wide test (`tools/export/test/export.test.mjs`) fails when any file names the outside workflow collection the core was first written from. Its one exception is credit a licence requires: the credit files a domain's `SOURCE.md` links from its Origin line, and no other file, the rest of that domain included. The test checks that one name only; the kit names other outside projects elsewhere: tools it installs, the sources in `docs/facts.md`, and programs and libraries a domain's text points to.

## Before you export

- Four local files must exist in `tools/export/`. All four are gitignored, and are never committed, printed or quoted:
  - `privacy.local.txt`, the deny list: people, clients, employers, private project names, personal identifiers (format in `privacy.local.example.txt`).
  - `owner.local.txt`, the owner's first name, which the export rewrites to "the owner" (format in `owner.local.example.txt`).
  - `private.local.txt`, the hub items and sources no committed file may name (format in `private.local.example.txt`).
  - `rewrites.local.json`, the studio-name rewrites (format in `rewrites.local.example.json`).
- The export refuses to run without any one of them. `npm test` must pass.

## The export routine

1. **Dry run:** `node tools/export/export.mjs --hub <path to the studio hub>`. It builds the catalog in a staging copy, runs every gate there, and changes the kit only when all of them pass. It also prints an `overlap:` line for each pair of shipped descriptions (skills, domain entries and their stubs, those Claude can start itself) that share two or more rare trigger words, words found in at most three of them (`tools/export/overlap.mjs`): two descriptions that claim the same request. That is a report, not a gate. A pair that `tools/export/overlaps.json` does not list yet is marked `overlap (new):`. Read it; where both should stay, say in the descriptions themselves which goes first, in the hub. Then add the pair to `overlaps.json`.
2. **Scan:** `node tools/export/scan.mjs` runs SkillSpector over every shipped skill, the kit's own skills (every folder under `.claude/skills`: `drill-to-adopt`, `setup-workspace`, `vet-and-adopt`), every shipped agent (`catalog/agents/<id>.md`, recorded as `agent:<id>`) and every domain (`catalog/packs/<id>`, recorded as `pack:<id>`) and records each verdict, score and every finding (rule, file relative to the item's folder, line, severity) in `tools/export/scans.json`, with `itemHash`, the hash of every file of the item as the scan read it (the hash `changelog.mjs` gives an item, with the whole "Last scan" line of a `SOURCE.md` left out, since the export writes that line from the scan); the next export writes them into each `SOURCE.md`. Every scan that recorded a finding, SAFE ones included, needs its section in `tools/export/scan-triage.md`: the heading `### <id>: VERDICT, N/100, K findings` (`### pack:<id>: ...` for a domain), then a table `| Finding | File:line | Verdict | Why |` with one row per finding, read at the line it names: the Finding cell starts with the rule, File:line is `file:line` (or `file` alone when the scanner gave no line), and the Verdict column says FP or BY DESIGN. A finding the scanner reports twice gets two rows. The export writes the counts and a link to that section beside the verdict. The script reads each report from the scanner's standard output (SkillSpector v2.13.6 refuses `--output` on Windows) and fails an item whose report says it suppressed findings (`suppressed_count` above 0), since those findings are missing from its list. It runs `skillspector` from the `PATH`; to run another command, set `SKILLSPECTOR_CMD` to it with its arguments, split on spaces, with quotes around a part that holds spaces and no shell involved, for example `SKILLSPECTOR_CMD="uvx --python 3.13 --from git+https://github.com/NVIDIA/skillspector.git@e2674da339b0bddc6e565d059c0577c6d9cd25da skillspector"` (the commit from `tools/export/scanner.json`).
   **Check without recording:** `node tools/export/scan.mjs --check` scans the same items, compares each item's findings with `scans.json` by rule, file and line, and writes nothing. Each difference is one line, `<key>: new <rule> <file>:<line>` for a finding the scan found and `scans.json` does not record, `<key>: gone <rule> <file>:<line>` for a recorded finding the scan no longer finds (`<file>` alone when the scanner gave no line); an item with no record, or a record that holds only a count, is a difference too, and so is an item whose content changed since its scan though its findings did not, `<key>: the item changed since its scan (itemHash <recorded>, now <current>); rescan and re-read its triage`. So are a verdict or score other than the recorded one, a finding whose severity changed at the same place, a scanner version other than the one the record names, and a record for an item no longer scanned. Record mode drops such a record and names it. Either mode refuses an item whose folder holds a name the export never ships (`.git`, `node_modules`, `__pycache__`, `.DS_Store`: `SKIP_NAMES` in `tools/export/item-hash.mjs`, the one list the build, the export's stage and the hash all use), with `<item>: holds <path>, which the export does not ship; delete it and scan again`: the scanner would read it, and its findings would be recorded against a file no adopter gets. A triage row can rest on text away from its line, which a change can reach without moving the finding: an AE1 row is at the line that links a file the scanner read only in part, and its verdict is a reading of that file. The last line counts the items and differences. Exit 0 when everything matches, 1 on any difference or an item that could not be scanned, 2 when the scanner cannot be started or the arguments are wrong.
3. **Release**, after the Linux check ("Check the scans on Linux before the release commit", below) has exited 0, and from a clean checkout of the hub, because a release refuses a hub with uncommitted changes in what the export reads: `git fetch origin --tags`, then `node tools/export/export.mjs --hub <clean hub checkout> --release X.Y.Z --note "What this release is about." --why "skill:<id>=Why it changed."`, one `--why` per changed item or folder ("History", below). A release also runs the content lint, and its `triage` gate compares each item's `itemHash` with the item as the export built it: an item changed since its scan, a record with no `itemHash`, or an item the export could not hash, fails until it is rescanned and its triage read again (a dry run does not compare hashes, since it has to write the changed catalog so that it can be scanned). It then writes the `CHANGELOG.md` section and `tools/export/state.json`, and sets `version` in `export.manifest.json`; set the same version in `package.json` yourself before the release run, so the release's files page lists it (`npm test` fails while the two differ). Its Added, Changed and Removed lists cover every item on the menu: a skill, agent or domain with its card, a practice (`practice:<id>`) with its card and the files it installs, and the outside item (`external:<id>`) with its card, so a changed card or template lists its item. An agent has no `SOURCE.md` to carry its last scan, so its recorded verdict, score and number of findings are part of what is compared. `state.json` says how it compared (`hashes`); one written in an older form is compared in that form, on the catalog items it tracked. The changelog is the full account of what a release ships: when maintainer-facing files changed since the last release (`tools/`, `.github/`, `docs/MAINTAINING.md`, the tests), add one more note that starts with "Maintainers:" and says what changed, even when adopters see no difference; a change visitors see on GitHub, such as the issue forms, also gets an adopter line. `git log --stat <last release>..HEAD -- tools .github docs/MAINTAINING.md` lists them. The adoption report form labels its issues `adoption-report`, and GitHub adds a label only when it exists in the repository: before the first release that ships the form, create it once on the public repository (`gh label create adoption-report --repo Richicinschi/studio-os --description "An adoption report, with its receipt"`), since `docs/trials.md` finds the reports by that label.

**No pull request runs the scanner, so a change to a scanned item is rescanned in the same pull request.** A change under `catalog/` or `.claude/skills/` (an agent is one file in `catalog/agents/`) is rescanned with the pinned scanner (`node tools/export/scan.mjs`, or that one item), its triage read again, and `scans.json` committed in the same pull request. `npm test` holds this, with no scanner, in each pull request's local run (see "Pull requests on the dev repository") and on all three systems in the release run: it compares `scanItemHashes` of the kit with every recorded `itemHash` and fails naming each changed item ("rescan it in this PR"). Otherwise the weekly `scan` run and the release's triage gate fail later.

**The CI job `scan`** (in `.github/workflows/test.yml`, with a 30-minute limit and no credentials left in its checkout) runs on the public repository only, since the dev repository runs no Actions: on a push to `release/**`, on a manual run (`gh workflow run test.yml --ref <branch>`) and every Monday at 05:17 UTC; never on a pull request or a push to `main`. It installs Python 3.13 and the SkillSpector commit `tools/export/scanner.json` pins with `pip`, prints `pip freeze` (the scanner's own dependencies are not pinned, so a difference can be traced to one of them), then runs `node tools/export/scan.mjs --check`. When you change `scanner.json`, change the job's `pip install` line and its Python version with it; `npm test` fails until they agree. The scanner's SC4 rule asks OSV.dev for known vulnerabilities at scan time, so the same scanner can find something new between two runs: a package's first advisory, or one that matches a pinned version. It does not see a new advisory for a version range it already flags: for a range it asks by package name and reports the same finding while the package has any advisory, so for those (the Astro starter site's `package.json` today) `npm audit` on an install, not the weekly scan, is the check. A red weekly `scan` therefore means "re-triage", not flaky CI: read the `new` and `gone` lines, rescan with `node tools/export/scan.mjs`, read every new finding, and update `scan-triage.md`; a finding that is real is fixed at its source or the item stops shipping, as for the triage gate.

**Check the scans on Linux before the release commit.** The dev repository runs no Actions, so without this step the public `release/vX.Y.Z` branch is the first place `scan.mjs --check` runs on Linux, and a verdict that differs by system shows only once that branch is public (v3.4.0 found one that way). Once the catalog and `scans.json` you will release are committed, run the check once in a Linux container with Docker, from your kit checkout (the folder that holds the `.git` folder, not a linked worktree):

```bash
docker run --rm --name kit-scan-linux -e COMMIT="$(git rev-parse HEAD)" -v "$(pwd -W 2>/dev/null || pwd):/src:ro" node:22-trixie bash -c 'apt-get update -qq && apt-get install -y -qq python3-venv >/dev/null && python3 -m venv /opt/scanner && /opt/scanner/bin/pip install -q "skillspector @ git+https://github.com/NVIDIA/skillspector.git@e2674da339b0bddc6e565d059c0577c6d9cd25da" && git config --global --add safe.directory "*" && git clone -q /src /kit && cd /kit && git checkout -q "$COMMIT" && SKILLSPECTOR_CMD=/opt/scanner/bin/skillspector node tools/export/scan.mjs --check'
```

`node:22-trixie` brings Node.js 22 and Debian's Python 3.13, the version `scanner.json` pins, and the scanner is installed from the commit `scanner.json` pins, as the CI job installs it. In Git Bash on Windows, put `MSYS_NO_PATHCONV=1` before `docker`, so the paths inside the container are not turned into Windows paths. The check reads a clone of the commit, never your working tree, so commit first; `safe.directory` lets git in the container clone a folder another user owns. It takes about 10 minutes (on 2026-11-25: 48 of 48 items checked, 0 differences) and exits 0 when Linux reads every item as `scans.json` records it. A difference is handled as for a red `scan` on one system ("When the publish stops", below): find the file, fix it at its source in the hub, rescan. Never scan the mounted folder itself: on a Windows checkout mounted into the container every file reads as executable, and on 2026-11-25 that gave 40 differences in 48 items where a clone of the same commit gave none.

**Moving to a newer scanner.** The kit records every scan with the one SkillSpector `tools/export/scanner.json` pins, so a newer version arrives as its own change, in this order:

1. **Pin it.** Find the release tag's full 40-character commit with `git ls-remote <the repository URL in scanner.json's install line> refs/tags/<tag>`: a lightweight tag gives the commit directly, and an annotated one also lists `<tag>^{}`, which is the commit. Edit `scanner.json`: `version`, `tag`, `commit`, `python` and the `install` line. Change the CI job's `pip install` line and Python version to match, and every install line in `cards/`, `docs/` and the kit's skills (the scanner gate lists each one still on the old commit). When `python` changes, also change the image of the Linux check above: `node:22-trixie` is there for the Python 3.13 that Debian 13 ships, and no gate ties the two. Check the new build with the `uvx` form of the install line (`uvx --python <python> --from` the install line's whole `git+…@<commit>` URL, then the scanner's command name and `--version`), which installs nothing on the machine: it must print the new version.
2. **Rescan everything with it.** Set `SKILLSPECTOR_CMD` to that `uvx` command, without its `--version` (on Windows with `PYTHONUTF8=1`) and run `node tools/export/scan.mjs`. Every entry in `scans.json` now records the new version. Run it a second time and compare the two `scans.json` files: a field that differs between the two runs on the same files cannot be recorded; drop it in `findingsFromReport`, with a test, and say why in `docs/facts.md`. Read the new report's shape too: when its fields moved, `verdictFrom` and `findingsFromReport` say so with an error naming the top-level fields, and are adjusted with a test.
3. **Re-triage every item.** Each item with any finding, whatever its verdict, gets its section in `scan-triage.md` rewritten from the new scan: every finding read at its file and line, one row each, FP or BY DESIGN and why. A reading from the old run can be reused only after the line itself is read again, and for an AE1 row (a referenced file the scanner read only in part) after that target file is read again in full, since the verdict is a reading of it; name the target file in the row's Why. A file the scanner read only in part in an item rated `CAUTION` at 0/100 with no finding is read again in full the same way. Update the run header (scanner version, date, the verdict counts). A finding that is neither FP nor BY DESIGN is a real defect: it is fixed at its source in the hub, or the item is withheld; it never ships with a row that says otherwise. The export's `triage` and `scanner` gates pass only when every recorded finding has its row and every entry has the pinned version.
4. **Check the cards and docs.** Cards that quote a scan (a verdict, a score, a count, a link to a triage heading) are brought to the new record, `docs/facts.md` gets the new version's facts (its report fields, what it refuses), and `node tools/export/card-tokens.mjs` reports 0 findings. `node tools/export/scan.mjs --check` with the same `SKILLSPECTOR_CMD` exits 0, and so does the Linux check ("Check the scans on Linux before the release commit", above, with the new commit in its install line). The CI `scan` job runs only on the public repository, so its first run on the new scanner is the release branch.
5. **Release.** The release export writes the new verdicts and triage links into every `SOURCE.md`, and its changelog says the scanner moved, with a "Maintainers:" line. Adopters install the new line from `cards/skillspector.md`; until they do, the comparer tells them their scanner is not the pinned one.

Exit codes: 0, done; 1, the build stopped (a malformed studio block, a rewrite entry that matches nothing, an unclassified hub item, an invalid manifest) or a gate failed, and the kit is unchanged; also 1 when every gate passed and the catalog was copied, but the kit is not a git work tree or git could not mark the scripts executable: the scripts are not marked, and a release wrote no `CHANGELOG.md` section and no `state.json`. Run the export again in the kit's git checkout. 2, refused before building (a missing local file, a `--note` carrying a denied term, path or secret, a dirty hub, or `--no-gitleaks` on a release).

**What an export leaves staged.** The kit's checkout has `core.fileMode=false`, so a script is executable only by its mode in the git index. After copying the catalog, the export runs `git add --chmod=+x` on every shipped file that starts with `#!`, which stages the script's content as well as its mode. After a dry run you do not keep, `git restore catalog` is not enough: it puts back the unstaged files, and the staged scripts keep their new content. The full undo is `git restore --staged --worktree catalog`, which also removes the scripts the export added; then delete by hand any new file `git status` still lists under `catalog/`.

**Studio rewrites** (`STUDIO_REWRITES` in `rules.mjs`, and `rewrites.local.json`) match in any case. Where the text matches an entry exactly as written, the replacement goes in as written, so an entry for "Zorvex app" turns "we ship Zorvex app" into "we ship this app"; at the start of a sentence, a list item or a paragraph it gets a capital ("Zorvex app ships." becomes "This app ships."). Where it matches only in another case and starts with a capital letter ("Hard rule 11" for the entry "hard rule 11"), it starts a sentence, and the replacement starts with a capital too. A replacement is never lower-cased.

## Check blocks, and the install cycle in the tests

A card's Check section may hold a fenced block with the info string `check`: `run:` lines, each a bash command run in the adopter's setup, each followed by an `expect:` line, the last line it must print; and `install:` lines, `<kit path> -> <setup path>`, which only the tests read. A command finds an item's recorded file with `installed <name>`, and the front door the item edited with `frontdoor` (its `AGENTS.md`, else its `CLAUDE.md`); it sees `SETUP`, `KIT` and `ID`. `tools/check-setup.mjs` runs the blocks for "check my setup". What a `run:` line may hold is an allowlist, in `lintChecks`: simple commands joined by `|`, `&&`, `||` or `;`, each starting with a reader (`test`, `[`, `grep`, `echo`, `ls`, `wc`, `head`, `tail`, `cut`, `tr`, `cat`, or a helper), `node` only as `node "$(installed <name>)"`, and `git` only as `git -C "$SETUP"` with `check-ignore`, `rev-parse`, `ls-files` or `config --get`; only the redirects `2>/dev/null`, `>/dev/null`, `2>&1` and `>&2`; no backslash, backtick, here-string, subshell or `$` other than `$SETUP`, `$KIT`, `$ID`, `$?` and `$( )`, whose inside is held to the same list. The content lint applies it to every card, and `check-setup` again before it runs a block. Add a block only for a **Claude:** step that reads, and prints one stable last line; a step for the person stays prose. `tools/export/test/card-checks.test.mjs` runs every block on a right setup and a wrong one, and fails when a card gains a block without them.

`tools/export/test/install-cycle.test.mjs` installs every skill, agent and domain in `catalog/`, by `vet-and-adopt`'s copy rules, and every card with `install:` lines, into a throwaway setup. Then it records the install, runs `check-setup` on it (it must pass), undoes it, and compares the setup with how it was. A new item that ships files joins the cycle by itself.

## The gates, and how to fix what they find

Fix the cause, never the gate.

- **secrets** (patterns, plus gitleaks): remove the secret at its source in the hub.
- **privacy** (the deny list, in file content and in file names; a finding names the list position, never the term): rewrite the hub text, or make the item `catalog-only` with the reason in its `note`.
- **paths** (studio paths, home folders, hostnames, private and public addresses): if it is a pattern, add a rewrite with a test in `rules.mjs`; otherwise make the item `catalog-only`. Upstream text that names a product but carries no studio detail can go on `PATHS_ALLOW` in `rules.mjs`: that one phrase in that one file, with the reason, reviewed.
- **risky** (unsafe patterns a shipped file would teach: an `allowed-tools` value that grants Bash or Write with no scope in parentheses, a container image or a package in a command pinned to the moving latest tag, a proxy or host setting that trusts every address with `"*"`): fix at the source in the hub, or add a `RISKY_ALLOW` entry in `rules.mjs` with its reason for a counter-example (text that warns against the pattern, a test fixture): that one phrase in that one file, reviewed. Never allow a hit that is real.
- **studioBlocks** (a studio block marker the build did not cut, in any shipped text file, scripts and data files included, in any spelling of its comment form; see "Studio blocks" below): fix the block in the hub. A Markdown file the build cuts never gets this far, because a malformed block stops the build.
- **markers** (studio words, as whole words, in any text file under `catalog/`, code comments included, except `catalog/DETECT.md` while it equals what `tools/export/detect.mjs` makes from `cards/` (this gate reads neither; every other gate reads both): "the hub", and "hard rule", "studio rule" and "studio hub" with their plurals (a possessive such as "the studio hub's" included), "this machine" and "his yes" in any case, and G1 to G8 in capitals only): rewrite the hub text, or add a `STUDIO_REWRITES` entry. A finding in `catalog/DETECT.md` means it no longer matches the cards: run `node tools/export/detect.mjs`, or fix the card it came from. A false hit, such as a regulator's guideline G6 or an upstream "Hard rules" heading, goes on `MARKERS_ALLOW` in `rules.mjs` as `{ file, phrase, why }`: that one phrase, on the flagged line, in that one file, reviewed.
- **names** (in every `.md` file under `catalog/`, fenced blocks skipped, a fence inside a `>` blockquote included (it ends at its closing fence or where its blockquote ends): a name in inline code that the studio has and the kit does not ship, any `[[linked]]` name the kit does not ship, and a name the studio has and the kit does not ship written as plain text in the front matter's `description`, as a whole word in any case): point the hub text at something the kit ships, or drop the name, or add a `STUDIO_REWRITES` entry for that file (as for `writing-great-skills`, whose description pairs with `vet-and-adopt` in the kit). In a description, only a studio name with a hyphen in it counts, since a one-word name such as "launch" or "pricing" is ordinary prose there; a private name counts at any shape. A name from outside the studio that is also the name of a studio item goes on `NAMES_ALLOW` in `gates.mjs` as `{ file, name, why }`: that one name, in that one file. A private name (on the private list, or in a hub pack whose `pack.json` says `public: false`) is reported without the name, and no allow entry passes it.
- **json** (every shipped `.json` file parses; a file that starts with a byte order mark fails too): fix the file in the hub.
- **accounting** (stray catalog files, files that are neither UTF-8 text nor a known binary, third-party skills without a licence, external items without one, diagram links that no longer match their `.drawio`): fix the file, add the licence, or regenerate the link.
- **links** (relative links must resolve, with the exact case, inside the kit): fix the link or the file name.
- **cards** (every menu item, meaning every `shipped` and `link-only` item and every practice, has its hand-written adoption card `cards/<id>.md`, and every card belongs to a menu item): write the card, or remove the orphan.
- **triage** (every shipped item whose last scan in `scans.json` recorded any finding, whatever its verdict, has one section in `scan-triage.md` with the same verdict and score, whose rows match the recorded findings one to one by rule, file and line, each FP or BY DESIGN; at a release, every shipped item also has a scan): read the findings and write the section. The gate compares the findings themselves: a recorded finding with no row fails, a row that matches no recorded finding fails, and so does a row judged anything else. A rescan that moves a finding to another line or file fails until its row moves with it. A heading's `K findings` must equal the section's number of rows, and a table with a Verdict column but no File:line column fails as a whole. A finding that is real is fixed at its source, or the item stops shipping; it never ships with the finding in it.
- **scanner** (the kit pins one SkillSpector in `tools/export/scanner.json`: its version, tag, full commit, Python version and install line; the export refuses to start without that file): every URL of the repository in a Markdown or JSON file outside `catalog/` must be exactly the git URL of `scanner.json`'s install line, the one at the pinned commit (the gate reads it from there): any scheme, host or case, with or without `.git` or an `@<rev>`, read with its percent-escapes decoded, and so must any URL of a file named for the scanner, such as a wheel on another host. Any install, download or run of the scanner by package name fails, whatever version it names (pip, pip3, `pip download`, `pip wheel`, pipx, `uv tool install`, `uv pip install`, `uv add`, poetry, conda, and `uvx` or `uv tool run` without a git `--from`): the name is not on PyPI (checked 2026-11-22), so whoever claims it would supply the code behind such a line. Only the git URL at the pinned commit passes, in `uv tool install`, in `uvx --from`, or after `pip install` as a direct reference to that URL, as the CI job has it; a plain link to the repository's page passes. The gate reads one line at a time, so it cannot see a command continued with a backslash on the next line (the name is still caught when it carries a version or stands alone on its line, but `uv tool install \` above a line `--python 3.13` and the bare name is not), nor a requirements file or lockfile, which it does not read at all (`pip install -r requirements.txt` passes whatever the file holds): keep install commands on one line, and the scanner out of requirements files; and every entry in `scans.json` must record the pinned version. Copy the install line from `scanner.json`, and rescan with the pinned version every item whose entry records another. A quoted upstream line that names the repository without the pin goes on `SCANNER_ALLOW` in `gates.mjs` as `{ file, phrase, why }`, like the kit's other allow lists: an occurrence passes only inside that phrase, in that file, wherever the line moves; an entry whose phrase is gone from its file fails the gate, so a removed quote leaves no standing allowance. `npm test` runs this gate on the kit itself. To move to a new scanner version, change `scanner.json` and every install line together, then rescan every gated item.
- **lint** (releases only, or `node tools/export/lint-content.mjs` at any time): module pages carry their front matter and five headings in order; cards carry `id`, `module` and `checked` and the eight headings in order, none empty, and hold at most 4,000 tokens (bytes divided by 4), each list item at most 150 words (fenced code not counted; an item runs on over blank lines while its text stays indented), since a card is read before its item is asked about and again when it is installed (a test record or a list of spellings goes to a test file or `SECURITY.md`, linked from the card); skill folders match their names; START-HERE gives a block per operating system; every front matter in a Markdown file is YAML that a real parser reads as the kit does (a plain value with ": " or " #" in it, or ending in ":", is quoted or folded); no file under `tools/`, `templates/` or `.claude/` holds a literal byte-order mark (the bytes EF BB BF; source writes the escape `\uFEFF`, and `catalog/` keeps upstream text as written); and the kit skills, START-HERE, ADOPT and the cards use none of the words that talk a step down ("just", "simply", "easy", "obviously", "should work", "guaranteed", "great question").

**Studio blocks.** A rule the studio relies on but the kit must not ship stays in the hub, inside a block: a line `<!-- studio-only -->`, the studio's text, a line `<!-- /studio-only -->`, then the generic text the kit ships. The build cuts each block, both marker lines included, from every shipped Markdown file before the rewrites run. Markers are whole lines (white space around them is allowed); a marker that shares its line with other text, is misspelt (a space, an underscore or nothing for the hyphen, in any case), opens a block inside another, closes no open block or is never closed stops the build with the file and the line, so a slip never cuts to the end of a file. Inline studio text is rewritten in the hub instead. Kit text that names the marker on purpose, like this paragraph, goes on `STUDIO_ALLOW` in `rules.mjs` as `{ file, phrase, why }`.

**Token figures in cards** are held to the files they describe by `npm test` (`tools/export/card-tokens.mjs`), with the estimator the kit uses everywhere (bytes divided by 4, rounded up). A skill or agent card states `tokens: description` and `tokens: body` in its front matter; a domain card states its entry and entry-with-agents sizes; every figure in a card's text ("the body, about 2,400 tokens") must be within 10% of the figure its sentence names: "description" or "every session", "body", "folder", a file's name, and for a domain "entry", "index" or an agent's name, or for a practice "light", "standard" or "full". The nearest of these words before the figure counts, or the nearest after it when none comes before; a figure in a sentence that names none fails, unless it is under 20 (a table row, one line): a figure under 20 is held to the word its sentence names like any other, and passes unchecked only when the sentence names none. In a domain card whose stub Claude cannot start, "by name" names 0 ("You start it by name: Claude cannot start it itself, so its description never loads and it costs 0 tokens every session."). In the front matter, only `description`, `body`, `light`, `standard` and `full` name a figure; any other key under `tokens:` names nothing. A figure that is not the size of a kit file (a threshold such as 1,000, a worked example, a measurement of something else, such as one line you add to your front door) goes in the card's front matter under `other_figures:` as a list. A card states no size in bytes: a figure followed by bytes, KB, MB or GB fails. Only a figure in bytes followed by "divided by 4" passes ("its 8,000 bytes divided by 4", the estimator spelt out); a KB, MB or GB figure fails even then. A documented limit that is not the size of a kit file, such as the 25 KB Claude Code reads of its auto memory, goes on `BYTES_ALLOW` in `card-tokens.mjs` as `{ file, phrase, why }`. The same check holds a card's lists to the shipped files: every script a domain ships (a file that starts with `#!` or ends in `.mjs`, `.cjs`, `.js`, `.py` or `.sh`) is named in its card by file name, and every backticked phrase in a list item led by a bold "Studio…" phrase ("Studio-specific wording.", "Studio references." and the like) occurs in the shipped item, in a file's text or as a file's path. After an export that changes a skill, run `node tools/export/card-tokens.mjs` and fix what it lists; the practice sizes (light, standard, full) are choices, so only their figures in the text are checked.

A new hub skill stops the export as "unclassified": add it to the manifest as `catalog-only` until the owner decides. A hub item that is never exported and whose very name must stay out of the kit goes, as `kind:id`, into the gitignored `tools/export/private.local.txt` (format in `private.local.example.txt`); the export counts it as private and no committed file names it. A hub source a page may not list, because its name would say what the studio works on privately, goes into the same file as `source <kit page> <hub path>`: staleness and the release's clean-hub check follow it, and the page's own `studio_sources:` leaves it out.

A studio pointer in a shipped copy whose rewrite would itself name what the studio works on privately (a product, a project, a data source) goes into the gitignored `tools/export/rewrites.local.json` instead of `STUDIO_REWRITES` (format in `rewrites.local.example.json`). Each entry also names a `gone` term: the build stops if that term is still in the file after the rewrites, and the export reports the entry by its number only. Put the same term on the deny list, so an export run without the file stops at the privacy gate.

The export needs four local files, all gitignored and never committed: `owner.local.txt` (the owner's first name), `privacy.local.txt` (the deny list), `private.local.txt` (hub items and sources no committed file may name) and `rewrites.local.json` (the studio-name rewrites). Each has an example beside it with invented entries. To export on another machine, copy all four there by hand. Without any one of them the export refuses to start and builds nothing, so a missing file can never ship what it protects; a file with no entries (`[]` for the rewrites) is a deliberate choice and runs. A `shipped` or `link-only` item, and every practice, also needs `importance` (core, recommended or optional) and a `why` of at most 140 characters, each either one value or one per profile (`{ "default", "data", "ml", "software" }`, the default required); a practice or an outside item needs `loads` (none, on-demand or every-session), and a practice its `files`. A practice whose files are not what loads, such as a hook's printed lines, states `everySessionTokens` itself. The export then writes `catalog/features.json` and `catalog/FEATURES.md` with each item's token estimate.

The adoption diagram is generated: edit the list in `tools/docs/adoption-sequence.mjs`, then run `node tools/docs/adoption-sequence.mjs docs`.

## Staleness

`studio_sources:`, in the front matter of the module pages, the examples, `START-HERE.md`, `ADOPT.md` and `PRINCIPLES.md`, lists the studio files the page was written from; the kit does not ship them, so a reader cannot open them, and the key's name says whose sources they are.

Every export lists the hand-written pages whose `studio_sources:` changed in the hub since the last release, and the pages whose `checked:` date is more than 90 days old. Re-check those facts against their sources, then update the date.

`docs/facts.md` is dated fact by fact instead (`tools/export/facts.mjs`). Each bullet carries the date it was last checked, after "checked", "read", "as of", "tried" or "observed ... on"; the lint refuses a bullet with none. A section named under `fast:` in its front matter (model names, plans, prices, claude.ai features) is due after 30 days, every other section after 90, and the export prints one `stale:` line per section with facts past their window. Re-check each of those facts on its source page, then write the new date into the bullet. What a vendor's pages do not say is a fact like any other: "<what>: not documented as of <date>; searched <the pages>", written only in `docs/facts.md`. The lint refuses the phrase "not documented" in every other Markdown file outside `catalog/`, this page and `CHANGELOG.md` excepted; a card links the facts section instead.

The CI job `links` (weekly, and by hand with `gh workflow run test.yml`) runs `node tools/docs/check-links.mjs`, which fetches every source link of `docs/facts.md`, its `references:` included, and fails on any that no longer answers. A red `links` run means a source page moved: find where it went, re-read the fact there, and update the link and the date. A release branch's run is a push run, so `links` shows there as skipped; it is not one of the checks a release waits for. A run by hand, such as the one for `scan` above, runs `links` too.

## Versioning

Semver. A new or changed item is a minor version. A removed item or a changed adoption protocol is a major version, because adopters' recorded decisions refer to them.

## History

The kit has two histories that never meet. The development history lives in a private repository, the `dev` remote; it holds every earlier version, private terms included, so it is never made public. The public repository, the `origin` remote, began on 2026-11-02 with one signed commit holding the v2.0.1 tree, and each later release adds one commit on top. Never push `main` to `origin`: the two histories share no commit, and the only way through would be a force-push.

**What a release commit holds, file by file** (public issue #66, the first of its three options). One commit per release cannot be read file by file, so each release after the first writes `docs/releases/vX.Y.Z.md`: every file that differs from the last release's tag, added, changed or removed, under the item it belongs to (a skill, agent or domain with its card, a practice with its template, a kit skill, a module page), or else under its folder, each group with one line of why. The why lines come from `--why "<group>=<text>"` on the release command, one per group, and pass the same gate as `--note`; a group without one says "Not given". A dry run before the release names the groups the page will have, and with `--why` lines, the groups still without one. A release is not run twice: to add why lines after it, `node tools/export/release-files.mjs page --previous <the release before> --release X.Y.Z --why "<group>=<text>"` writes the page again on its own. Commit everything the release run leaves, and change nothing after it: before the release commit is published, `node tools/export/release-files.mjs check <the release before> <release commit>` compares the page with what the commit really changes, and prints each file that differs. The changelog section links the page. The comparison needs the last release's tag in this checkout: a release stops until `git fetch origin --tags` has brought it. The other two options, one public commit per item and developing the hand-written parts in the open, were not chosen: the first gives the same information with more commits to publish, and the second needs every hand-written file kept clean of private terms in a public history, which the export now checks only at release.

## Publishing a release

**Pull requests on the dev repository.** CI does not run on the private dev repository. The workflow is the same file there and still starts on a push or a pull request, but on a private repository its `test` job runs on Linux only, since GitHub counts Windows minutes twice and macOS minutes ten times against a private repository's allowance, and the public repository's three job names stay as its ruleset requires them; when the allowance is spent, GitHub does not start the jobs at all. A dev pull request merges on a local `npm test` run, on Node 22, and on Windows with Git Bash first on the `PATH` (in PowerShell, `$env:PATH = "C:\Program Files\Git\bin;$env:PATH"` before `npm test`; without it the plugin command test is skipped as `no Git Bash`), with the result posted as a comment on the pull request. The three-system gate is the public repository's run on `release/vX.Y.Z`, below, before `main` moves there.

Day-to-day work and every release commit go to `dev` through a pull request (above). After a release has passed every gate (`--release` runs gitleaks and the lint), publish its tree as one commit on top of `origin/main`. Build that commit in a separate worktree on a detached HEAD, so `main` and its gitignored local files stay where they are and no local branch has to move. The commit goes first to a branch `release/vX.Y.Z` on `origin`, where the test workflow runs its tests on Linux, Windows and macOS and its `scan` job; `main` on `origin` moves only after that run is green. Then the release commit gets a signed annotated tag, and the GitHub release is made from that tag. From your kit checkout:

```bash
git fetch origin
git worktree add --detach ../studio-os-public origin/main   # the first time only
cd ../studio-os-public
git switch --detach origin/main                     # start from what is published, on no branch
git rm -r -q .                                      # empty the index and the folder of tracked files
git checkout <release commit> -- .                  # the release tree, every file
git commit -S -m "Studio OS vX.Y.Z"                 # message: the version; the story is in CHANGELOG.md
git verify-commit --raw HEAD 2>&1 | grep -qE '^\[GNUPG:\] VALIDSIG .* 991E180986B77CE992993AEB2E926BA88C6D6423\s*$' && echo "release key" || echo "STOP: not signed by the release key"
test "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <release commit>^{tree})" && echo "same tree" || echo "STOP: not the release tree"
test "$(git rev-list --count origin/main..HEAD)" = 1 && echo "one commit" || echo "STOP: not exactly one new commit"
node <your kit checkout>/tools/export/release-files.mjs check <the release before> <release commit> || echo "STOP: the files page differs from the release"   # every file the commit changes is on its page
rulesets_active() { gh api "repos/$(gh repo view "$(git remote get-url origin)" --json nameWithOwner --jq .nameWithOwner)/rulesets" --jq '[.[] | select(.enforcement=="active") | .name] | sort | join(",")' | grep -qx 'Protect main,Protect tags'; }   # the two rulesets of the table below, both active, and no other; a shell function, so paste this line again in every new terminal
rulesets_active && echo "rulesets active" || echo "STOP: rulesets not active"
rulesets_active && test "$(git rev-list --count origin/main..HEAD)" = 1 && test "$(git rev-parse HEAD^{tree})" = "$(git rev-parse <release commit>^{tree})" && git verify-commit --raw HEAD 2>&1 | grep -qE '^\[GNUPG:\] VALIDSIG .* 991E180986B77CE992993AEB2E926BA88C6D6423\s*$' && node <your kit checkout>/tools/export/history-check.mjs "origin/main..$(git rev-parse HEAD)" && git push origin HEAD:refs/heads/release/vX.Y.Z || echo "STOP: release branch not pushed"   # the first public push: only with the rulesets active, one commit, the release tree, the release key and no private term; starts the tests on the three systems, and scan
gh run list -R "$(git remote get-url origin)" --event push --branch release/vX.Y.Z --workflow test.yml --commit "$(git rev-parse HEAD)" --json databaseId --jq '.[0].databaseId'
gh run watch <run id> -R "$(git remote get-url origin)" --exit-status && rulesets_active && git verify-commit --raw HEAD 2>&1 | grep -qE '^\[GNUPG:\] VALIDSIG .* 991E180986B77CE992993AEB2E926BA88C6D6423\s*$' && git push origin HEAD:main || echo "STOP: main not pushed"   # main moves only on a green run, with the rulesets active, for a commit the release key signed
git tag -s vX.Y.Z -m "Studio OS vX.Y.Z"             # a signed annotated tag on the release commit
git verify-tag vX.Y.Z                               # the signature, for you to read
git verify-tag --raw vX.Y.Z 2>&1 | grep -qE '^\[GNUPG:\] VALIDSIG .* 991E180986B77CE992993AEB2E926BA88C6D6423\s*$' && test "$(git rev-parse vX.Y.Z^{commit})" = "$(git rev-parse origin/main)" && git push origin vX.Y.Z || echo "STOP: tag not pushed"   # final: a pushed tag can never be moved or deleted
gh release create vX.Y.Z -R "$(git remote get-url origin)" --verify-tag --title "Studio OS vX.Y.Z" --notes-file <section>
git push origin --delete release/vX.Y.Z             # you run this one yourself, see below
```

Expected: `release key`, `same tree`, `one commit`, then `rulesets active` (the two rulesets of the table below, "Protect main" and "Protect tags", are both active and are the only active ones; the push of the release branch and the push of `main` each check it again), then `history-check: 1 commit(s) checked ...; 0 carry at least one` and the push of the release branch, with no `STOP: release branch not pushed`, then the run's id, then `gh run watch` ending with all five jobs passed (`test (ubuntu-latest)`, `test (windows-latest)`, `test (macos-latest)`, `test-node-24` and `scan`) and exit code 0, then a plain push of `main` with no force and no `STOP: main not pushed`, then `git verify-tag` printing `Good signature` with the release key on its `using RSA key` line (`991E180986B77CE992993AEB2E926BA88C6D6423`, the fingerprint in [SECURITY.md](../SECURITY.md)), then the tag pushed as `[new tag]` with no `STOP: tag not pushed`, then the release's address, then the release branch deleted. A `STOP` line, a term found, any count other than 1 commit checked, or a `git verify-tag` without that good signature stops the publish: a range with no commits passes `history-check` while checking nothing, which is why the count check comes first. `<section>` is a file holding this version's section of `CHANGELOG.md`, the release notes.

The range `origin/main..<commit>` is exactly what the push to `main` publishes, so `history-check.mjs` checks that and nothing else. It runs from your kit checkout, because it reads the local files of the checkout it lives in; that checkout shares its objects and `origin/main` with the publish worktree but not its HEAD, so the commit is named by its id. It checks the commit's whole tree, its file names and its message against the owner's name, the deny list and the private item and source names, and prints term numbers only. Given `origin/main` alone, it checks the whole public history. Both checks come before the first push, because the release branch is public as soon as it exists.

If `gh run list` prints nothing, the run has not started yet: wait a few seconds and run it again. If no run appears within a minute, the workflow did not trigger: stop, and do not push `main`. Deleting the release branch is a command you run yourself: the kit's [git-guardrails](../cards/git-guardrails.md), where it is installed, refuses every remote delete (`push --delete`) when Claude runs git.

**The run id.** `--event push --branch release/vX.Y.Z` keeps only the run the push to the release branch started. Without them, `.[0]` can be another run of the same commit: once `main` moves, its push starts a second run of `test.yml` on that commit, and for v3.3.0 the unfiltered list's first entry is that `main` run. `scan` is a job of `test.yml`, so watching this one run waits for all four required checks on the release commit, and for `test-node-24`, the tests on the newer Node.js line: the ruleset does not require that job, but `--exit-status` fails the watch when it fails, so it stops a release as well.

**The tag.** `gh release create` makes the tag itself when none exists on `origin`, and the tag it makes is a plain one, with no signature: that is how v3.2.0, v3.2.1 and v3.3.0 got plain tags. So the tag is made here, signed and annotated, and pushed before the release; with `--verify-tag`, `gh release create` refuses when the tag is not on `origin`, instead of making a plain one. The tag comes after `main` moves, so it only names a commit `main` already holds. Once pushed it is final: "Protect tags" refuses moving or deleting a tag, so a mistake in a pushed tag cannot be fixed by tagging again. So the push runs only after two checks pass: the release key made the tag's signature (`git verify-tag` exits 0 for a good signature from any key you hold), and the tag names the commit on `origin/main`. Until that push, the tag is local and `git tag -d vX.Y.Z` removes it. The same fingerprint check follows `git commit -S`, because `-S` signs with whatever key `user.signingkey` names.

**The GitHub setting behind each step.** The local lines (the release-key checks of the commit and of the tag, the tree, the count, `history-check`, `git verify-tag` and `rulesets_active`, which reads the settings below but changes nothing) are checks you make; nothing on GitHub repeats them. The pushes are held by the public repository's settings:

| Step | Setting on the public repository | What it refuses |
|---|---|---|
| The run on `release/vX.Y.Z` | Actions: `allowed_actions: selected`, which allows GitHub's own actions and those in the account's own repositories (`github_owned_allowed: true`, `verified_allowed: false`, no patterns), and `sha_pinning_required: true` | A workflow that uses an action from neither GitHub nor the account's own repositories, or one not pinned by its full commit id, ends in `startup_failure` with no jobs, so the commit gets no checks and `main` refuses it as missing them |
| `git push origin HEAD:main` | Ruleset "Protect main", `required_status_checks`: `test (ubuntu-latest)`, `test (windows-latest)`, `test (macos-latest)` and `scan`, with "Require branches to be up to date" off | A commit that does not have each of the four checks passed on that very commit; the release branch's run is what gives it them |
| `git push origin HEAD:main` | Ruleset "Protect main", `required_signatures` | A commit without a signature GitHub can verify against a key on the account, any of its keys; the `release key` line checks which key |
| `git push origin HEAD:main` | Ruleset "Protect main", `non_fast_forward` and `deletion` | A force push of `main`, and deleting it |
| `git push origin vX.Y.Z` | Ruleset "Protect tags" (every tag), `update`, `deletion` and `non_fast_forward` | Moving a tag that exists, and deleting one |
| `git push origin vX.Y.Z` | None for the tag's own signature: "Protect tags" has no `required_signatures`. On a tag ruleset GitHub applies that rule to the commits a tag push brings, not to the tag, so a release tag on a commit `main` already holds passes it signed or not ([docs/facts.md](facts.md), "GitHub rulesets and Actions settings, tried 2026-11-21") | Nothing about the tag; `git verify-tag` above is the only check of its signature |
| `gh release create --verify-tag` | None: the flag | A release whose tag is not on `origin` |
| `git push origin --delete release/vX.Y.Z` | None: no ruleset covers `release/**` | Nothing; that is why the branch can be deleted |

Neither ruleset has a bypass actor, and none is ever added: not to get a release out, not for one push. Nor is a rule turned off or a ruleset switched to evaluate mode for a release. A push a ruleset refuses prints `remote: error: GH013: Repository rule violations found for refs/heads/main.` (or `refs/tags/vX.Y.Z`), then a link to the repository's rules, then a `remote: - ` line for each rule the push broke: `- <n> of <m> required status checks are expected.` for checks with no run on this commit, `- Required status check "scan" is failing.` for a failed one, `- Commits must have verified signatures.` followed by the id of each unsigned commit. Then come `! [remote rejected] HEAD -> main (push declined due to repository rule violations)` (for the tag, `vX.Y.Z -> vX.Y.Z`) and git's `error: failed to push some refs`. A tag push can instead be refused with `remote: error: GH006: Protected tag update failed for refs/tags/vX.Y.Z.` and `(protected tag hook declined)`, as the trial saw once; it is handled the same way. The lines as the trial printed them are in `docs/facts.md`. A tag that already exists on `origin` is refused by git itself, as `! [rejected] vX.Y.Z -> vX.Y.Z (already exists)`. Nothing that push sent was published. What to do is below, by cause.

**When the publish stops.** Up to the push of `main`, `origin/main` has not moved, and the commit you built is on no local branch: when you give up an attempt, `git switch --detach origin/main` in the publish worktree is the only local undo. Then, by cause:

- **A term found, or a `STOP` line before the push to `release/vX.Y.Z`:** nothing was pushed. Fix it in the kit, release again (below), and start over. `STOP: not signed by the release key` needs no new release: point `user.signingkey` at the release key, then build the commit again from `git switch --detach origin/main`.
- **A red run:** do not push `main`. If the infrastructure failed rather than a test or the scan (a runner that did not start, a download that timed out), run the failed jobs again on the same commit with `gh run rerun <run id> -R "$(git remote get-url origin)" --failed`, then watch the run again. Otherwise (a failed test, or a `scan` whose verdicts do not match the release's recorded ones) delete the release branch yourself (`git push origin --delete release/vX.Y.Z`), fix the cause in the kit, release again, and start over.
- **A red `scan` whose verdict differs from the record, though `scan.mjs --check` on Windows matched:** the scanner can fail closed on one system only. When its `analysis_completeness` is partial there (a path it resolves differently, such as `./...` on Windows), it raises a verdict it keeps on another system. Delete the release branch yourself (`git push origin --delete release/vX.Y.Z`), as for a red run: otherwise the next push of it is rejected. Scan the item with `--format json` on each system and compare `analysis_completeness.ledger_exceptions`: the entry on one side only names the file and the reason. Fix the content at its source in the hub so that the analysis is complete on both, rescan, run the Linux check ("Check the scans on Linux before the release commit", above) and release again; never edit the record to match one system.
- **`STOP: rulesets not active`:** "Protect main" or "Protect tags" is missing or not `active`, or another ruleset is active beside them, so the pushes below would not be held as the table says. The chained pushes check the same thing and refuse to run. Apply the settings in the table under "The GitHub setting behind each step" (no bypass actor, no evaluate mode), then run the steps again from the `rulesets_active` line. `rulesets_active: command not found` (or `bash: rulesets_active: command not found`) means the function is not defined in this terminal, not that the settings are off: paste the `rulesets_active() { … }` line again, then run the line that stopped.
- **`STOP: release branch not pushed`, with no push output above it:** one of the checks chained before the push failed, and nothing was pushed. The `rulesets active`, `release key`, `same tree` and `one commit` lines name the failed check; when all four passed, `history-check` printed its own line with the terms it found. Handle it as `STOP: rulesets not active` above, or as a term found or a `STOP` line before the push to `release/vX.Y.Z`. If git printed a refusal above the `STOP` line, the push ran and was refused: see the next case.
- **The push to `release/vX.Y.Z` is rejected:** a branch from an earlier attempt is still there. Delete it, then push again. Never force.
- **`STOP: main not pushed` after a green run, with no push output above it:** the rulesets check or the release-key check failed. Run `rulesets_active && echo "rulesets active" || echo "STOP: rulesets not active"` again: when it stops, apply the settings as for `STOP: rulesets not active` above, then run the `gh run watch` line again; the release branch can stay. Otherwise the release-key check failed, but the release branch is already public. Delete the release branch yourself (`git push origin --delete release/vX.Y.Z`), then do as for `STOP: not signed by the release key` above, and start over.
- **The push of `main` is refused (GH013):** the remote lines name the rule. A required check that is missing or failed is a red run, above; check that the run you watched was for this commit. A commit without a verified signature was built without `-S` or with another key: delete the release branch yourself, build the commit again from `git switch --detach origin/main`, and start over.

After the push of `main`, the release commit is public and only the tag and the release are left:

- **`STOP: tag not pushed`, with no push output above it:** a check failed and the push did not run, so the tag is local only. `git verify-tag vX.Y.Z` shows which key signed it; `git rev-parse vX.Y.Z^{commit} origin/main` shows whether it names the published commit. `git tag -d vX.Y.Z` removes it; fix the cause (the signing key in `user.signingkey`, or a HEAD that is no longer the release commit), tag again, and go on from `git verify-tag`. If git printed a refusal above the `STOP` line, the push ran and was refused: see the next case.
- **`git push origin vX.Y.Z` is refused:** stop. Do not make the release, never delete the tag on `origin`, never force, and never add a bypass actor. Compare `git ls-remote origin refs/tags/vX.Y.Z` with `git rev-parse vX.Y.Z`: if they show the same id, your tag is already on `origin` and you go on to `gh release create`. Otherwise `origin` holds another tag of that name, and it stays: publish the fix as the next patch version.
- **`gh release create` refuses because the tag is missing:** the tag push did not go through. Push the tag, then make the release. Never drop `--verify-tag`: without it the release makes a plain tag of its own.

**Releasing the same version again.** A release writes its `CHANGELOG.md` section and `tools/export/state.json`, the snapshot the next release compares against. In the fix commit on `main` in your kit checkout, put both back as they were before the failed release (`git checkout <release commit>^ -- tools/export/state.json CHANGELOG.md`), then run `--release X.Y.Z` again with the same notes and commit the result as the new release commit. Without that, the second run compares against the release that was never published: its section says "No catalog changes" and sits above a second section for the same version.

The workflow file in the pushed commit decides what runs, so the gate holds from the first release whose `.github/workflows/test.yml` lists `release/**`. Before that, these steps used a local branch `public`; it is no longer needed. Once the publish worktree is detached, `git branch -d public` deletes it, and refuses if it holds a commit `origin/main` does not have. Because `main` requires the `scan` check, a commit whose workflow has no `scan` job cannot reach `main`.

## Pull requests on the public repository

The public repository runs Dependabot alerts and security updates, CodeQL code scanning and secret scanning, so Dependabot can open pull requests there. Never merge a pull request on the public repository, Dependabot's included: the next release commit replaces the whole tree with the release tree, so a change that exists only on `origin` disappears at that release. Make the change where its file comes from instead (a file under `catalog/` in the hub, anything else in this repository), release and publish, then close the pull request if it is still open.
